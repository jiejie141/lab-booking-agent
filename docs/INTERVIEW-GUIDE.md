# 智能实验室预约 Agent：面试讲解与演示指南

> 本文依据当前项目代码整理。第一人称话术请按你实际负责、理解和验证过的工作调整。项目目前是可运行的演示工程，没有真实企业上线规模或用户增长数据；不要编造业务收益。

## 一、30 秒介绍（可以直接练习）

这是一个智能实验室预约系统，解决的是设备预约冲突之后，用户还要反复换时间、换设备的问题。用户可以直接填写预约，也可以通过自然语言表达需求。系统会检查设备状态、培训资质、开放时间和已有预约；遇到冲突时，会生成可比较的备选方案，并解释每个方案调整了哪些条件。技术上采用 FastAPI、LangGraph 和 SQLAlchemy，核心原则是模型负责理解语言，业务规则和数据库负责保证预约正确。

## 二、2—3 分钟完整介绍

我会从业务闭环介绍这个项目。实验室设备不仅有时间冲突，还有资质、开放时间和设备状态等限制。普通预约表单往往只告诉用户不能预约，这个项目希望进一步回答：在保证资质等硬性条件的前提下，有没有代价更小的替代安排？

系统有三个主要入口：直接预约、对话预约和规范检索。学生可以查看实验室与设备、创建和取消预约；管理员通过权限控制处理审批、管理用户和查看审计等信息。对话流程用 LangGraph 编排，先解析意图和预约条件，缺信息就追问，信息完整后检查约束；冲突时进入协商，用户确认方案后再次校验并下单，最后生成回复。取消和规范查询有自己的分支。

我认为最值得展开的有三点。第一是可解释的约束协商，按调整时间、缩短时长、同实验室换设备、跨实验室换设备逐级寻找候选，给每个候选记录放宽条件，并保留不同类别的选择。第二是并发正确性，不能只靠先查后写，而是把预约拆成占用时间格，用数据库唯一约束防止重叠写入，配合事务和冲突重试。第三是模型边界，模型不能决定用户身份，也不能绕过资质检查，真正写入前必须经过领域规则复核。

前端使用原生 HTML、CSS 和 JavaScript，支持流式对话、方案确认、角色权限显示和失败反馈。登录首页加入了可操作的协商时间轴，用一个例子解释产品价值。当前本地演示使用 mock 模型路径，真实模型接入和线上效果评估需要分别验证，不能把 mock 测试当作真实模型准确率。

## 三、整体结构：从页面到数据库

端到端例子：“明天下午两点预约荧光光谱仪两小时。”身份取自登录令牌；解析器提取设备、日期、开始时间和时长；缺条件则追问；领域层检查资质和设备可用性；冲突则返回含取舍说明的候选；用户确认后重新校验，因为候选生成后时段可能被别人抢走；事务成功后返回预约结果。

## 四、三个技术深挖点

### 1. 约束协商为什么有价值？

把条件分为硬条件和可协商条件。培训资质等硬条件不能放宽；时间、时长、同类设备和实验室可以按策略调整。当前采用确定性候选枚举和加权扣分排序，日期也会尝试当天、次日、前一天和后两天。候选记录 `relaxations`，让用户比较改变了什么；结果选择还兼顾类别多样性，避免所有推荐都是挪时间。

这是可解释的规则策略，不是训练出来的推荐模型，也不保证整个资源调度问题的全局最优。未来可用用户确认率、调整幅度和实际反馈来校准排序权重。

### 2. 怎么避免两个人同时预约成功？

“先查询没冲突，再插入预约”存在竞争窗口。核心保证是占用格表在设备、日期、时间格维度有唯一约束，让数据库原子地拒绝冲突。预约和占用格在事务中处理；遇到竞争，重新查询并给出冲突结果。时间必须遵守统一粒度，才能把区间重叠转换成格子冲突。

PostgreSQL 的事务级 advisory lock 用于减少同设备请求的冲突重试；SQLite 不依赖这个锁，正确性仍由占用格唯一约束承担。不能声称“加了 Python 锁就支持多进程并发”。

直接预约接口还支持用户范围内的幂等键，避免同一个请求重试产生重复预约。它解决的是特定写入入口的重复提交，不等同于全系统 exactly-once。

### 3. Agent 怎么做到可控？

自然语言只是业务入口。模型提供结构化需求或工具调用意图，业务层负责执行和校验。登录身份由后端令牌决定，不接受对话文本自行指定身份；下单前复核资质、设备状态、开放时间等规则；模型异常返回友好提示并记录内部日志，不直接把供应商报错细节给用户。

默认路径是确定性的 LangGraph 工作流。代码也提供可选 ReAct 执行模式和降级机制，但不能把两种执行策略称为多个独立 Agent 协同。默认流程更适合规则明确、写入敏感的预约任务，ReAct 的灵活性需要用预算、工具边界和评估约束。

## 五、面试官常见追问

**这和普通 CRUD 有什么区别？** 预约记录仍然是 CRUD；差异在自然语言多轮补全、冲突后的可解释备选和规范问答。确定性下单能力独立保留，不强迫所有操作都走模型。

**为什么用 LangGraph？** 因为流程存在追问、分支和多轮状态，显式节点方便定位问题和测试。不是所有业务都需要 Agent；直接预约入口用普通 API 更清楚。

**数据库查询与 RAG 怎么分工？** 设备状态、预约和资格查结构化数据库；实验室安全规范等文档走检索。默认 BM25，中文按字符二元组处理；可选向量和混合检索，通过 RRF 融合排名，以来源、标题和正文指纹去重。检索到规范不代表模型可以据此覆盖数据库规则。

**如何处理登录退出后的旧回复？** 前端取消在途请求，并用会话代次检查旧响应，防止前一个身份的数据重新写回页面。服务端通过 `token_version` 支持使旧令牌失效，按钮隐藏只是体验，权限检查必须在服务端。

**SSE 能解决什么？** 让等待过程和回复增量可见。流结束不等于业务事务一定成功，必须根据服务端结果展示状态；退出或切换会话时需终止旧流。它不是消息队列。

**怎么测试？** 领域规则和 API 自动化测试验证业务行为，浏览器检查验证登录、方案交互和窄屏布局。模拟模型用于可重复测试；真实模型还需单独评估理解准确性、非法工具调用、延迟和成本。PostgreSQL 并发行为要在真实 PostgreSQL 环境单独验证。

**能直接上生产吗？** 不能据本地演示这样承诺。还需要真实模型评估、生产数据库验证、部署与监控、跨机器会话和限流状态治理等。当前默认进程内状态、可选本地共享方案不等同于跨机器 Redis 架构；没有依据宣称支持大规模水平扩展。

**还有哪些外围能力？** 资质准入、审批、审计、预约过期与爽约处理、数据库支持的通知重试以及健康和指标端点。它们完善业务闭环，但没有引入分布式消息队列或完整分布式追踪。

**你做了什么？** 根据实际分工回答：“我重点负责/参与了……，我能展开……的实现与测试。”可以说明使用 AI 辅助设计、编码和检查，并解释自己如何验证结果。不要把不理解的模块说成独立完成。

## 六、5 分钟演示顺序

1. 首页点击三个步骤或播放演示，说明“冲突以后仍有选择”；明确这是本地交互示例。
2. 选李娜演示账号，登录后查看设备，展示直接预约入口和对话入口。
3. 输入一个设备预约需求，缺时间时补充时间，解释多轮信息合并。
4. 如需展示冲突，先在专用演示数据中准备已占用时段。比较备选方案的取舍，确认前说明会再次校验。避免为了演示污染正式数据。
5. 切换张伟展示资质边界；管理员展示审批与审计。不要只演成功路径。
6. 结束时主动说明 mock 模式、没有生产流量验证，以及下一步真实模型评估与跨机器状态治理。
