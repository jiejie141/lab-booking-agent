## 一、真实弱点（按会被追问的严重度排序）

### 1.1 🔴 停用/降权后，已签发的令牌仍然有效 —— **我实测复现过**

复现步骤（已在本机跑通）：

```text
1. 建用户 zz_probe3，登录拿到 token
2. 管理员停用该账号 → "active": false
3. 用同一账号密码重新登录 → 401  ✓（新登录确实被挡住了）
4. 但拿第 1 步的旧 token 继续请求：
     GET  /api/auth/me      → 200
     GET  /api/reservations → 200
     POST /api/agent/chat   → 200   ← 仍然能下单
```

**根因**：`api.py:637-658` 的 `current_user` 只做密码学验签，**从不回查数据库**。
`User` 表只有 `password_hash`，**没有 `is_active`、没有 `token_version`**
（`grep -n 'class User' -A 30 src/lagent/models.py` 可当场验证）。
`catalog.py:193-203` 的 `deactivate_user` 只清空口令哈希，停不掉已发出的令牌。
令牌 TTL 120 分钟（`config.py:146`），所以最长有 **2 小时窗口**。

更严重的一档：**降权同理**。管理员把某人从 `admin` 降成 `user`，
旧令牌 payload 里的 `role` 仍是 `admin`（`security.py:276` 从令牌读角色），
过期前继续享有管理员权限。

**被问到怎么答**（承认 + 说清边界 + 给方案，不要辩解）：

> 「这是真实缺陷，我确认过。`current_user` 只验签不查库，所以停用只挡新登录、
> 挡不住已发出的令牌 —— 最坏 2 小时。修法是把角色和停用状态挪到**可失效的载体**上：
> 用户表加 `token_version`，签发时写进 payload，`current_user` 回查比对；
> 版本一变旧令牌全废，停用就把版本 +1。代价是每请求多一次主键查询，
> 而这个查询本来就要为审计做，不算额外开销。
> 它记在我的 `docs/OPEN-ISSUES.md` 待办里，我没有假装它不存在。」

**关键**：这一条**必须自己先说出来**。面试官先发现的话，性质就从
「他知道自己的边界」变成「他没发现」。

### 1.2 🔴 门禁凭证用裸 SHA-256，与口令的 scrypt 不一致

同一个仓库两套标准：

| 用途 | 实现 | 位置 |
|---|---|---|
| 登录口令 | `scrypt`（参数写进哈希串，可升级） | `security.py:89-107` |
| 门禁凭证（能开门的通行证） | `hashlib.sha256(plain)`，单轮**无盐** | `access.py:417-418` |

**被问到怎么答**：

> 「这是取舍，但选得不够好。当时的理由是凭证本身是 192 bit 随机数
> （`_CREDENTIAL_BYTES = 24`），熵够高、不可爆破，所以没上慢哈希。
> 这个判断对**防爆破**成立，但漏了**纵深防御**：库一旦泄露，
> 无盐 SHA-256 挡不住同明文比对。正确做法是加服务端 pepper 的 HMAC，
> 或直接走 scrypt —— 凭证校验频率远低于登录，慢哈希的代价完全付得起。
> 两套标准不一致本身就是设计味道，我会统一到 scrypt。」

**更细的一处**：`credential_fingerprint` 取哈希串**前 16 个 hex**
（`access.py:421-424`），注释只说「不可逆推明文」，没提它其实是
**同一个 secret 的摘要截断**；每次刷卡都写进 `AccessEvent.credential_fingerprint`
（`models.py:724`）。更干净的是独立随机 event id，或用另一个 HMAC 密钥算指纹。

### 1.3 🟠 登录限流能被绕过（三道都验过）

`LoginThrottle` 是纯进程内字典（`ratelimit.py:97-158`），key 是
`IP#username`（`api.py:800`）。三个真实绕过：

1. **多 IP 打同一账号**：key 含 IP → 每个 IP 独立配额 → 账号可被无限尝试。
   注意它只锁「IP+用户」组合，**不锁账号本身**（`ratelimit.py:105-108` 自己承认了）。
2. **登录接口没有 IP 维度的频率限流**，只有失败计数。
3. **反代之后** `request.client.host` 恒为网关 IP；`api.py:776-779` 明确不解析
   `X-Forwarded-For`，把这件事推给了网关。

**答法**：

> 「进程内限流的边界我写在 docstring 里了：重启清零、多副本配额翻倍。
> 更实际的问题是 key 含 IP —— 攻击者用代理池就能对同一账号做无限尝试。
> 该补的是**按账号**的独立失败计数（跨 IP 累计，可由管理员解锁），
> 限流状态本身挪到 Redis 或共享库。X-Forwarded-For 的口径我选择了不自己解析，
> 因为应用层永远无法判断来自网关的 XFF 是否已经被客户端伪造 ——
> 这个责任应该在网关，代码里写死了这个前提。」

### 1.4 🟠 没有 logout / 令牌撤销（与 1.1 同源）

全仓没有任何服务端 `logout`/`revoke`/`blacklist`/`jti` 实现；
前端 `app.js:1062` 只是清掉本地 sessionStorage。
令牌一旦泄露，用户**没有任何手段立即失效它**，只能等 2 小时。

> 「和 1.1 是同一个根因，一起修：有 `token_version` 或 `jti` 黑名单，
> logout 就是一次版本自增或黑名单写入。现在没做，因为单机 demo 场景下
> 我认为 refresh token + 吊销列表是一整块工程量，不想只做一半 ——
> 但「只做一半」也比没有强，这是我判断失误。」

### 1.5 🟡 审计日志可被能连库的人篡改

`AuditLog` 是普通表（`models.py:479-500`），没有 hash chain、没有签名、
没有 append-only 触发器。也就是说：**系统全部追责能力建立在一张谁都能 UPDATE 的表上**。
另外 `audit.py:99` 的 `detail` 承载用户输入（取消理由、用途等），
`sweep.py:364` 还会按 90 天保留期**主动删除**审计（`config.py:311`）。

> 「审计的**不可抵赖性**我没做。现在它防的是『误操作留痕』，不防『有库权限的人删痕』。
> 要做的话加哈希链（每条记录含前一条的摘要），或写外部 append-only 存储。
> 保留期删除是有意的 —— 但那意味着审计不是永久凭证，这个前提得写清楚。」

### 1.6 🟡 口令哈希没有升级路径（rehash-on-login）

`hash_password` 把 scrypt 参数写进哈希串（`security.py:89-107`），
`verify_password` 会读存储参数验证 —— 这两步做对了。
但 `verify` 之后**从不重算**（`api.py:824-825` 登录成功只 verify）。
所以管理员调高 `LAB_PASSWORD_KDF_N`（`config.py:149`）后，存量哈希永远停留在旧成本。

> 「参数随哈希存储，所以升级是**可能**的，缺的是触发点：verify 成功后比较
> stored 参数和当前配置，不同就用新参数重算并落库。十行左右的事。」

### 1.7 🟡 `api.py` 2691 行，是个上帝模块

`src/lagent/api.py` 2691 行，是全仓第二大文件的近 3 倍
（第二大 `domain/access.py` 967 行）。所有 33 条路由都挤在一个文件里。
测试也直接 import 内部（`tests/test_api.py:515` 等 4 处 `from lagent import api as api_module`）。

> 「路由层按领域拆成 `routers/` 是应该做的。没做的原因是它不会导致功能错误，
> 而我当时把时间投给了并发正确性和边界文档 —— 事后看这个优先级我仍然认为是对的，
> 但拆包在下一个迭代就该做，越晚拆迁移成本越高。」

63 个提交里 62 个落在 2026-09-23 ~ 09-29，之后只有零星几个。

## 二、你最该拿去讲的三段故事

这三段都有代码可指、有命令可跑、有取舍可讲 —— 是「我做过项目」和
「我理解工程」的分水岭。面试官问「讲一个你解决过的难题」时，从这里挑一个。

### 2.1 ★ 区间重叠超卖：从「加了锁」到「闸在数据库」

**这是全项目最好的故事，强烈建议主推。**

**问题**：部分唯一索引建在 `(equipment_id, date, start_time)` 上，只能挡住
**开始时间完全相同**的重复预约。`13:00-15:00` 和 `14:00-16:00` 开始时间不同，
索引看不见它们重叠 —— 20 并发下**双双写入**，超卖。

**为什么压测没发现**：`main.py loadtest` 的 40 个并发用的是**同一个开始时间**，
正好走唯一索引能覆盖的路径。所以「并发安全」这个结论此前只在一种情形下成立。

**现场可跑**（这句话本身就是加分项 —— 你有可复现的脚本）：

```bash
./.venv/Scripts/python.exe scripts/overlap_race.py
# 三种情形各 20 并发，期望都是「恰好 1 条成功」
```

脚本头部 `scripts/overlap_race.py:1-28` 就把根因写清楚了。

**根因**：`acquire_equipment_lock` 在 SQLite 上是**空实现**
（`booking.py:212-215` 直接 `return "none(sqlite)"`），而当时的注释写着
「写事务天然互斥」—— 于是「锁内复检」退化成了典型的 check-then-act：
两个事务各自读到「无冲突」，再用不同的 `start_time` 写入。

**修复**（`models.py:13-27` 有完整推导）：把「区间」拆成「不可再分的格」。
预约按 `slot_granularity_minutes`（默认 30 分钟）展开成若干条 `ReservationSlot`，
唯一索引打在 `(equipment_id, date, slot_index)` 上。
这样**任何形式的相交**（部分重叠 / 包含 / 完全相同）都必然撞唯一索引，
而且**与数据库无关** —— SQLite 与 PostgreSQL 行为一致。

**为什么不用 PG 的 `EXCLUDE USING gist (tsrange(...) WITH &&)`**：
那是 PG 上更优雅的解法，但 SQLite 没有等价物，本地开发就跑不起来。
这是「一次实现、两种库都对」的取舍，代价是多一张表。

**这段故事的正确讲法**（照着说）：

> 「我一开始把并发正确性寄托在应用层的一把锁上，注释还写着『写事务天然互斥』。
> 后来我写了个复现脚本，发现那把锁在 SQLite 上**是空实现** ——
> 注释描述的是 PostgreSQL 的行为，而本地跑的是 SQLite。
> 所以真实的防护是 check-then-act，20 并发下确实超卖。
> 修的时候我没有去加强那把锁，而是把不变式**下沉到数据库**：
> 把区间展开成占用格，唯一索引打在格子粒度上 ——
> 这样正确性不依赖任何应用层判断，也不依赖数据库种类。
> 教训是：**应用层的『先查后写』在并发下必然有窗口，判断该放在有原子性的地方。**
> PostgreSQL 上我仍然保留 advisory lock，但它的角色变了 ——
> 只是减少重试次数的优化，不再承担正确性。」

**如果面试官追问「那为什么不直接上 PG」**：

> 「因为我要本地开发和 CI 都能跑。而且这个问题**不是 PG 特有的** ——
> 换 PG 用 gist 也能解，但那就把正确性绑死在一种数据库上。
> 占用表是更便宜的代价：多一张表，换两种库行为一致。」

### 2.2 ★ 三次「本地绿、CI 红」—— 三个不同的机制

`docs/OPEN-ISSUES.md:72-74` 记了同一天三轮 CI 失败，**三个根因完全不同**。
这段的价值在于：它证明你会区分「flake」和「真 bug」。

| 轮次 | 表面现象 | 真实根因 | 教训 |
|---|---|---|---|
| 第一轮 | `mypy` 报 `Settings(_env_file=...)`，但 **pytest 全过** | 本地只跑 `mypy src`（40 文件），CI 跑的是 pyproject `files` 配置的**全量 85 文件** | 本地必须跑与 CI **同名**的命令 —— 它们查的根本不是同一批文件 |
| 第二轮 | `test_clock` 只在 CI 红：`assert 28799.99 < 120` | 差值恰好 8 小时。`now_local()` 是**配置时区**的墙上时间，测试却用 naive `datetime.now()`（**宿主机**时间）。本机 UTC+8 恰好相等，CI 的 TZ=UTC 差 28800s | 拿「本机跑得绿」当验证，量出来的只是「本机时区恰好没踩中」 |
| 第三轮 | `ruff` 在 CI 红、本地绿 | **本地 venv 根本没装 ruff** | 本地静态检查要装齐 CI 工具链，缺哪一层哪一层就只靠 CI 兜底 |

**为什么这段特别值钱**：它说明你不是「看到红就重跑」，而是**每次都追到机制**。
而且第一轮的修法是个亮点 —— 没有加 `type: ignore`（全仓 0 处是硬指标），
而是改用仓库既有写法（`monkeypatch.setenv` + `reset_settings_cache`）。

**讲法**：

> 「我有一天连着三次 CI 红、本地全绿。如果当成 flake 重跑就学不到东西了，
> 所以我每次都追到机制 —— 结果是三个完全不同的原因：
> 文件集不同、时区依赖、工具链缺失。
> 最让我警醒的是时区那个：本机是 UTC+8，CI 是 UTC，
> 本地绿不是『代码对』，只是『本机恰好没踩中』。
> 之后我把时区、路径分隔符、文件名大小写这三类东西都归到
> 『本地绿不算数』那一档。」

### 2.3 ★ 一个「自己制造假信号」的监控缺陷

这个故事的独特性在于：**是监控自己骗了监控**。

**问题**：新增 SQLite 状态后端后，`/metrics` 里 session 同时报出
`memory` 和 `sqlite` 两条序列。于是告警规则 `LagentStateBackendSplitBrain`
（`deploy/prometheus-alerts.yml`）在**单副本**上误报「已扩容、状态分裂」。

**根因**：`SqliteSessionStore` 继承基类，基类构造先报 `memory`、子类再报 `sqlite`。
**修复**：后端由**类属性** `_BACKEND` 决定，构造期只报一次；
模块级兜底单例加 `report_backend=False`（import 期还不知道进程会用哪个后端）。
加了两条回归用例钉住（`tests/test_metrics.py::TestStateBackendIsObservable`）。

**讲法**：

> 「我加了一个告警规则来检测『多副本导致状态分裂』，结果它在单副本上就响了。
> 查下来是我自己埋的指标在撒谎：子类构造时先报了父类的后端名，
> 于是同一个组件在一个进程里出现了两条序列。
> 这件事的教训比 bug 本身重要：**埋点必须保证『一个组件一个进程一条序列』，
> 否则它亲手制造出自己要检测的信号** —— 那种假信号会让整条告警链失去可信度。」

## 三、问答脚本（按面试官会问的顺序）

### Q1「介绍一下这个项目」 —— 30 秒版

> 「一个实验室预约 Agent，Python 后端。核心差异不是『让大模型抽字段』，
> 而是**预约失败时给出带取舍说明的备选方案** —— 不是回一句『该时段不可预约』，
> 而是告诉你放宽哪一条约束能约上。
> 16,984 行源码配 15,073 行测试，1,026 项用例全绿，
> 33 条 REST 接口带 OpenAPI 契约门禁，CI 四类作业含 PostgreSQL 真实链路。」

**如果对方只给一分钟**：直接开控制台演示（见 `docs/DEMO-SCRIPT.md` 的 60 秒版）。
演示比描述有效十倍。

### Q2「这跟普通 CRUD 有什么本质区别？」

> 「区别在**失败路径的信息量**。普通 CRUD 返回成功/失败；
> 这里失败要回答『为什么失败、怎么才能成功』。
> 而且约束分两类，走不同代码路径：
> **资质不够是硬约束** —— 换时段解决不了，所以模型不该给时间建议，
> 它会直接说『缺少离心准入资质，需先通过培训』；
> **时段冲突是软约束** —— 可以放宽，于是返回按可行性排序的 5 个方案，
> 每个都标注放宽了什么（`shift` / `switch_equipment`）。
> 这个区分是产品逻辑，不是模型能力 —— 模型只做语言层。」

**当场可验**（这两条命令的对比很有说服力）：

```bash
# 张伟只有「光谱」资质
# 问离心机 → 硬约束，0 个方案：
#   「这个需求不是换个时间能解决的：缺少「离心」准入资质」
# 问荧光光谱仪（他有资质但时段被占）→ 软约束，5 个方案带放宽说明
```

### Q3「测试这么多，是不是在测自己的测试？」（★最高频）

**这是最危险的追问，必须正面回答。**

> 「您问到了要害。1,026 项里模型是 **mock** 的，所以它证明的是
> 『业务逻辑与状态机自洽』，不是『模型效果好』。
> 数据库里**确实**有用例在自我循环 —— 比如某些 API 测试只断言状态码。
> 但骨架部分是真断言：并发用 20 个并发任务断言『恰好 1 条落库』，
> 迁移用例在旧 revision 上**先造数据**再升级，断言数据还在、新列取默认值。
> 真实模型评测我没做，因为需要外部 API key —— 这一条写在未解决清单里，
> 报告自带免责声明，我没有把它当准确率引用。」

**主动交代两个具体缺口**（自己说出来 = 诚实；被问出来 = 掩饰）：

- **没有覆盖率度量**：仓库里没有任何 coverage 配置。所以「1,026 项」是
  **数量**不是**覆盖**，我不该让这两个概念混在一起。
- **有 92 处 `assert status_code == 200` 这类只断言状态码的写法**
  （全仓 2,016 条 assert 里的 92 条）。它们能防回归，但证明不了语义正确。

**如果面试官继续压「那你怎么知道测试有效」**：

> 「一个可操作的判据：我做过**注入式验证** —— 故意把业务逻辑改错，
> 看测试红不红。红说明有效，绿说明这个用例是摆设。
> 我没有系统性做这件事，这是方法上的欠缺。」

### Q4「并发安全怎么保证的？」

→ 直接讲 §2.1 的完整故事。**这是你最强的一题**，不要只答「我加了锁」。

### Q5「多副本部署行吗？」

> 「**同机多进程已经解决**：设 `LAB_STATE_BACKEND=sqlite` 后，会话与限流计数
> 落同一个 WAL 文件，脚本与服务并存、`uvicorn --workers` 都不会各算一份配额
> （`tests/test_state_store.py` 用两个独立实例验证了共享）。
> **跨机器不行** —— 那需要 Redis。我没有假装 SQLite 解决了分布式。
> 但我把这件事**做成了可观测的**：组件构造时自报 `lagent_state_backend`，
> 多副本时同一组件会出现多条序列，告警规则会响 ——
> 也就是说『该扩容了』这个事实不用靠人记得，指标会说出来。」

这段回答的结构特别好：**已解决 / 未解决 / 未解决的那部分如何被发现**。

### Q6「如果流量涨 100 倍会怎样？」

> 「会先堵在单进程上，两个原因：
> 一是长请求（5–30 秒的模型调用）没有队列化，直接占着 worker；
> 二是没有分布式追踪，慢在哪只能靠结构化日志拼。
> 这两条我在 `docs/OPEN-ISSUES.md` 第 17 条明确写了『不做』并给了理由 ——
> 与当前规模不匹配。真要做的话顺序是：先上队列把长请求异步化，
> 再把限流与会话外置到 Redis，最后才是多副本。
> 先做多副本是最糟的顺序 —— 会把状态分裂问题放大 100 倍。」

### Q7「安全做到什么程度？」

**先讲做对的**（这些我都验过）：

- JWT 手写但关键点齐全：`alg` 强校验防 `alg=none`（`security.py:197-198`）、
  `exp` 强校验且缺 `exp` 直接拒（`210-216`）、签名比对用 `compare_digest`（`207`）、
  失败信息统一不泄漏（`api.py:647-653`）
- 防账号枚举：登录失败走 `_dummy_hash()` 等价成本（`security.py:266-276`）
- IDOR：`api.py:1729/1857/2144` 三处都「静默改写为自身」，服务端不信任客户端的 `user_id`
- 无 SQL 注入（全仓无拼接 SQL）、无 SSRF（唯一外呼 URL 来自硬编码 config）
- 密钥 fail-closed：默认密钥**拒绝启动**，有测试（`tests/test_hardening.py:304`）

**然后主动交代弱点**（§1.1、§1.2）—— 顺序很重要：先说做对的建立可信度，
再说弱点展示自知。**反过来会显得心虚。**

### Q8「你从这个项目学到什么？」

不要答「学会了 FastAPI」。挑一条有认知升级的：

> 「最大的收获是**『本地跑得绿』不是验证**。
> 我的时区 bug 在本地永远是绿的，因为本机恰好 UTC+8；
> mypy 在本地永远是绿的，因为我查的文件集和 CI 不一样。
> 这两件事让我意识到：验证的**可信度**取决于环境，而不是取决于命令有没有报错。
> 所以后来我坚持本地跑与 CI 同名的命令，也把『本地绿不算数』的清单写进文档。」

### Q9「如果你重做一遍，会改什么？」

> 「三件事，按优先级：
> 一是**令牌失效机制从第一天就做** —— `token_version` 是十行的事，
> 后补却要动认证主路径，代价大得多；
> 二是**路由层一开始就拆包** —— `api.py` 2691 行，越晚拆迁移成本越高；
> 三是**上覆盖率度量** —— 我一直用『测试数量』当质量代理，
> 但数量衡量的是投入，覆盖率才衡量缺口。」

这题答得好会显著加分 —— 它证明你有**反思能力**而不只是执行力。

### 4.2 「测试∶源码 ≈ 1∶1」要小心

15,073 / 16,984 ≈ 0.89，说「接近 1:1」不算撒谎，但**行数包含 fixture 和参数化数据**，
所以这个比值会比「真实测试逻辑占比」高。

**更稳妥的说法**：「952 个测试函数覆盖 35 个模块，共 1,026 个用例」——
函数数比行数更难注水，也更经得起追问。

如果被问「有多少是真断言」：**如实答** —— 全仓 2,016 条 `assert`，
其中 92 条是只断言状态码的弱断言。

### 4.3 「14/14」这行数字必须删掉

`python main.py eval` 的输出第一屏就是：

```text
⚠ 本轮**不是**真实模型：下面的三个百分比衡量的是链路自洽，
   不是模型准确率 —— 请勿引用到简历 / 答辩 / 汇报等对外材料。
```

**这是项目自己打印的警告。** 把它写成简历数字，一旦被追问
「模型接的哪个、prompt 怎么调的、为什么准确率 100%」，会当场崩。

**替代写法**：「14 条评测用例覆盖 8 类意图；mock 模型下端到端链路自洽，
真实模型评测待接 API key」。承认没做比虚报一个数字安全得多。

## 六、一句话总结

这个项目的竞争力**不在于功能多**，而在于：

1. 有一个**真正的技术差异点**（约束协商，且区分硬/软约束）；
2. 有一个**带复现、根因、可移植修复的并发缺陷故事**；
3. 有一套**诚实的边界文档**（18 条问题 14 条闭合、4 条明说不做）；
4. 数字**都能当场对着代码核实**。

面试时最该传递的信号是：**我知道我的系统哪里不行，以及为什么**。
这个信号比「我的系统什么都行」可信得多。
