## 0. 先说清楚一件事：这个系统的预约入口是什么

> 本节记录的是评估当时（`5d1cb05`）的状态。**已过期，见上方复评。**

当时全仓的写接口只有 5 个（`src/lagent/api.py`）：

```
POST /api/auth/login        POST /api/reservations/cancel
POST /api/agent/chat        POST /api/access/verify      POST /api/access/issue
```

**当时没有 `POST /api/reservations`。** 预约的唯一入口是
`/api/agent/chat` → LangGraph → `tool_create_reservation`（`agent/graph.py:322`）。
控制台 `web/index.html` 也只调了 `/api/agent/chat`。

也就是说：**当时用户必须"用自然语言跟模型说一句话"才能预约成功。**
这一条决定了下面很多判断 —— 它不是一个"选日期 → 选时段 → 提交"的表单系统。

> **现状**：`POST /api/reservations` 已补上（`26b6d50`），
> 复用 `domain/booking.py` 的全部不变式；对话入口降级为"可选的便捷方式"。
> 这一条同时把"模型挂了系统就瘫"的风险解掉了。

## 2. 并发与预约冲突处理 —— 达标

这一块是**全项目最扎实的部分**，可以放心。

- **不变式压在数据库层**：`reservation_slots` 部分唯一索引 + `lab_occupancy` 唯一索引，
  并发写入靠 `IntegrityError` 裁决（`domain/booking.py:380-391`），不靠应用层"先查再写"。
- PostgreSQL 下额外用 `pg_advisory_xact_lock(hashtext(...))`（`booking.py:201-206`）减少重试。
- SQLite 下明确标注 `acquire_equipment_lock()` 返回 `"none(sqlite)"` —— **没有假装加锁**。
- 实测：`overlap_race.py` 3/3 未超卖；`loadtest -c 40 -r 3` 三轮 40 并发**每轮恰好 1 成功**。
- 失败结果有 7 种机器可读分类（`ok / not_found / invalid / forbidden / state / conflict / contention`），
  `conflict`（写入前复检就发现坑没了）与 `contention`（只有唯一索引拦住且重试耗尽）**刻意分开** ——
  前者该多给替代时段，后者该扩容，合并了就丢了修的方向。

## 3. 角色权限与数据安全 —— 部分达标

**做对的（这部分达标）：**

- `user_id` **一律从令牌取**，请求体里的同名字段被覆盖 —— 越权在服务端就断了，不靠前端自觉。
- 非管理员查预约时传 `user_id=别人` 会被**改写为自己的 id**（`api.py:928`）。
- 401（没认证）与 403（认证了但权限不够）严格分开。
- 防账号枚举：账号不存在与口令错误返回**完全相同**的 401。
- 口令用 scrypt，且放到线程池跑（不卡事件循环）。
- 写接口 `extra="forbid"` + 长度上限；请求体 64KB（读之前就拒）；CORS 默认**空**白名单。
- 审计独立事务、失败与拒绝也记。
- 专项测试：冒烟 [3][4] 越权读写、[5] 令牌伪造（改 role / alg=none / 过期）、[6] 身份不可伪造。

**拉低到"部分达标"的两条（都是上线阻断级）：**

1. ~~**默认 JWT 密钥是 `dev-insecure-secret-change-me`**（`config.py:98`），
   启动只打一条 WARNING（`api.py:215`）**然后照常运行**。
   任何人拿到这个公开仓库的默认值，就能**伪造任意用户乃至管理员令牌**。~~
   → **已整改**（`645c8d9`）：未设置即拒绝启动，退出码 3；显式开关下每次启动打 CRITICAL。
2. ~~**登录无限流、无失败锁定**，只做了审计记录。~~
   → **已整改**（`b609fc7`）：按「来源地址 # 用户名」计数锁定，
   过期锁会丢掉旧失败记录（否则用户重试的瞬间又被锁）。

## 4. 部署与运维 —— 部分达标

**做对的：**

- 依赖极其克制：`requirements.txt` 只有 fastapi / uvicorn / langgraph / sqlalchemy / alembic /
  pydantic / tzdata / httpx / pyyaml。scrypt + HS256 + BM25 + Prometheus 文本格式**全是标准库自实现**，
  少三条供应链。控制台是零依赖单文件 HTML。
- 配置齐全：`LAB_*` 环境变量 + `.env.example` 逐条带注释（包括"为什么是这个默认值"）。
- **日志与指标是超配的**：JSON 单行 + `request_id` 贯穿访问日志/审计/门禁 + 入站 id 白名单校验；
  `/metrics` 出 p95/错误率/限流/预约结果分类/模型耗时/清扫心跳；健康检查分存活/就绪/业务三档。
- 数据生命周期有治理：过期预约收尾、凭证超时收尾、审计 90 天 / 流水 180 天归档（先落盘后删除）。

**不达标的：**

- ~~**备份：零实现。** 全仓 grep `backup / 备份 / restore` 在 `src/` 与 `scripts/` 下零命中。~~
  → **已整改**（`1158c23`）：`main.py backup`（PG 走 `pg_dump`、SQLite 走 `VACUUM INTO`）
  + `main.py restore` + 恢复演练用例。
- **compose 未实机验证（仍存在）。** 我实测只做到 `docker compose config` 静态解析通过

- 默认数据库是 SQLite（`config.py:77`），单文件、单进程；生产形态（PG）配置写了但没验过。

## 5. 性能与稳定性 —— 部分达标

**做对的：** 降级链设计得很诚实 ——
react → deterministic → 引导式表单三级，且**能说清边界**：它只覆盖"模型不听话"，
不覆盖"模型不在"（后者明确 502 + 前端切表单，不是编造一个假的成功）。
失败响应不含堆栈与内部路径。

**风险项：**

- **单进程单 worker**（`uvicorn.run`），`/api/agent/chat` 真实模型下是 5–30 秒长请求，
  占着 worker 不放，**无队列化 / 无 202 异步**。
- **会话状态在进程内存**（`agent/state.py:72` `SessionStore`）：重启即丢、多副本会漂移。
- **限流是单进程的**：多副本部署等于把配额乘以副本数（`README` 已自述）。
- ~~**`GET /api/reservations` 无分页**：`list_reservations`（`booking.py:506`）不带 limit，
  管理员不传 `user_id` 时返回**全量**。~~
  → **已整改**（`5dc4aa0`）：可选 `limit`/`offset`，总数走 `X-Total-Count` 响应头。
  返回形状**刻意保持数组**没改信封，避免所有既有调用方一起改。
- 无 refresh token，令牌 2 小时到期要重登。

## 结论 3：最小可用整改范围

目标不是"做成完美系统"，而是**达到一个院系能真用起来的下限**。

**必修（4 项，约 2–3 周）：**

1. **安全默认值 fail-closed** —— `LAB_JWT_SECRET` 未设置时拒绝启动；
   令牌密钥移出 `.env`（至少 Docker secrets）。**半天可完成，收益最大。**
2. **备份与恢复** —— 增加 `main.py backup`（PG 用 `pg_dump`，SQLite 用 `VACUUM INTO`），
   配套定时任务 + **恢复演练一次**（没演练过的备份不算备份）。
3. **确定性下单接口** —— 新增 `POST /api/reservations`（选时段 → 提交 → 确认），
   复用现有 `domain/booking.py` 的全部不变式。**对话入口保留为"可选的便捷方式"**，
   但不能是唯一路径。这一条同时把"模型挂了系统就瘫"的风险解掉。
4. **后台维护 CRUD** —— 实验室/设备/用户的增删改（哪怕先只做管理员后台 + 导入），
   把"改代码重新 seed"这条路堵掉。

**建议一并做（2 项，约 1 周）：**

5. **简化版审批** —— 不要做工作流引擎。加一个 `requires_approval` 标记在设备上，
   预约落到 `pending`，管理员在后台"通过/驳回"两按钮即可。
   （状态机常量现成，`STATUS_PENDING` 已经在 `ACTIVE_STATUSES` 里了。）
6. **最低限度通知** —— 只做预约成功/取消/驳回三种，**邮件一种通道**即可，
   先不做短信与微信。关键是"有"而不是"全"。

> **复评**：上面 1–6 全部已整改（commit 见上方表格）；第 7 条"黑名单自动化"
> 也已一并做了（`11ee0e8`）—— 判定建立在门禁流水上、且**默认只记录不处罚**，
