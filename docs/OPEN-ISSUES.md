## P1

### 1. 预约不能改期 / 续约

| | |
|---|---|
| **模块** | `domain/booking.py` · `api.py` · `web/index.html` |
| **表现** | `PATCH /api/reservations/{id}` → **404**（全仓没有这个路由）。用户想挪时间只能「取消 + 重新约」。 |
| **影响** | **取消是不可逆的**：时段当场释放，别人立刻能抢。而重约可能已经约不上 —— 一次「改个时间」的操作，可能让用户同时失去旧时段和新时段。这是日常使用里最先被抱怨、也最容易补的缺口。 |
| **排查/解决** | 新增 `reschedule(reservation_id, start, end)`，复用 `create_reservation` 的同一套六道约束与占用格逻辑。**顺序是这条的关键**：先占新坑、成功后再释放旧坑；新时段不可用则原样保留旧时段并在响应里给出协商阶梯（与 `conflict` 一样给替代方案）。要新增 reason 分类、补并发回归（两个用户互相改期不能互相吃掉），控制台加「改期」按钮。 |

### 2. 门禁不校验实验室开放时间

| | |
|---|---|
| **模块** | `domain/access.py`（`open_hours` 在此文件里**零命中**） |
| **表现** | 实测：23:24（周六，分析楼 301 的 `open_hours` 周末是 09:00-18:00）用管理员签发的凭证刷卡 → `granted=True · 已入场`。全仓没有 `lab_closed` 这类拒绝码。 |
| **影响** | **下单**路径严格卡开放时间（六道约束之一），**门禁**完全不看 —— 两者不对称。正常流程下凭证窗口来自预约（⊆ 开放时间），所以问题只出在**手工签发**这条路径，而手工签发正是「访客 / 临时人员 / 忘记预约的补救」用的，恰恰是最该谨慎的场景。对需要换鞋套、有生物安全要求的实验室，凌晨放人进去是安全问题不是方便问题。 |
| **排查/解决** | 在 `verify_entry` 里加一条「当前时刻是否落在该 lab 的 `open_hours`」，新增 `lab_closed` 拒绝码（与 `permit_expired` / `no_permit` 并列，别混用）。**要顺带拍一个板**：管理员是否允许显式越权？建议允许，但强制带 `override_reason` 并写进审计 —— 否则「夜间取样」这类真实需求会被逼成"把凭证窗口开到 23:59"。 |

### 3. HTTP 错误响应只有人话，没有机器可读的分类

| | |
|---|---|
| **模块** | `api.py` 的 HTTP 边界（`_BOOKING_STATUS` 只用来选状态码，没带出去） |
| **表现** | `409 {"detail":"该时段刚被占用：2026-09-29 16:00-17:00"}` · `422 {"detail":"你缺少「离心」准入资质，…"}`。进程内其实有 7 类 `BookingOutcome.reason`，**过 HTTP 边界就丢了**。 |
| **影响** | 前端要区分「换个时段」和「去补资质」只能去解析中文文案 —— 而这正是项目自己在 `BookingOutcome` 的 docstring 里明确反对的做法：*"抓『从人话里找关键词』当分类依据，是典型的「改一句文案，指标就静默错位」"*。进程内守住了这条原则，**API 契约上漏了**。 |
| **排查/解决** | 错误响应体加一个字段即可（`_BOOKING_STATUS` 已经算出 reason 了，顺手带上）：`{"reason":"conflict","detail":"…"}`。这是**纯加成**改动，老客户端不受影响。控制台那两处按 `reason` 分支的地方可以顺便简化。 |

### 4. 通知只进库不出库，且没有全系统视图

| | |
|---|---|
| **模块** | `notify.py` · `sweep.py` · `api.py` · `web/index.html` |
| **表现** | 实测积压 **20 条全部 `pending`**（`LAB_SMTP_HOST` 为空 → 只记录不投递）。`/api/notifications` 默认**只返回本人**，管理员要看别人的必须逐个指定 `user_id`；**没有「全系统待发」的视图**。另外该端点硬编码 `.limit(200)` 且**不告知被截断**。 |
| **影响** | 学生等不到审批结果邮件只会来问人；管理员手上没有能回答「到底发出去了没有」的地方。通知列表被截到 200 条而界面上看不出来，会让人以为"只有这些"。 |
| **排查/解决** | 三件事，都小：① **已有**（今天加的 `notifications` 健康检查报告是否积压）；② 给 `/api/notifications` 加管理员的「全系统待发」查询（`user_id` 缺省 + `status=pending`）；③ 列表返回总数或 `truncated` 标志，别静默截断。若要真的发邮件，配 `LAB_SMTP_HOST`/`LAB_SMTP_FROM` 即可，代码路径已通。 |

### 5. 限流与会话在进程内存

| | |
|---|---|
| **模块** | `ratelimit.py`（`SlidingWindowLimiter` 用进程内 dict）· `agent/state.py`（`SessionStore` docstring 明写"**进程内**会话"） |
| **表现** | 两者都没有共享存储。 |

| **触发条件** | 出现横向扩容需求时。重新评估的三条条件写在 `DELIVERY-READINESS.md` 的 P2-10。 |
| **排查/解决** | 扩容之前先把限流换成 Redis/共享存储、会话外置（或加粘性会话）；这一步做完再谈多副本。 |

### 6. 下单没有幂等键

| | |
|---|---|
| **模块** | `domain/booking.py` · `schemas.py`（`grep -rin idempot src/` 无实现） |
| **表现** | 请求体没有客户端生成的幂等键。 |
| **影响** | 客户端重试 / 用户双击会产生两条预约。**注意失败形态不是"都会撞唯一索引"**：同一时段重试会被挡（409），但**换了一个时段的重试**会真的多出一条 —— 那是一条用户没打算下的单。 |
| **排查/解决** | `POST /api/reservations` 加可选 `idempotency_key`；`reservations` 上加 `(user_id, idempotency_key)` 部分唯一索引；命中已存在的键就**回放首次结果**而不是报冲突。 |

### 7. 「给有数据的表加列」只演练到第二条 revision

| | |
|---|---|
| **模块** | `migrations/versions/` · `tests/test_migrations.py` |
| **表现** | `TestSecondRevisionOnPopulatedTables` 是**唯一**一个"先造数据再升级"的测试，覆盖 `0001 → 0002`。而 `0003`（equipment 加 `requires_approval`）与 `0005`（reservations 加 `no_show_at`/`pardoned_at`）**同样是加列，却没有对应的演练** —— 测试里的升级发生在**空表**上。 |
| **影响** | 生产库是有数据的，所以第一次真实升级将是那条路径第一次真正执行。"SQLite 的 ADD COLUMN 一般安全"—— 但"一般"不是"验过"，而这个项目的风格是把"一般"变成"验过"。 |
| **排查/解决** | 把那个测试参数化到 0003/0005（复用同一套 `_seed_rows_at_0001` 思路：先在旧 revision 上插入数据，再升到 head，断言数据仍在且新列取到默认值），并**在 PostgreSQL 上也跑一遍**（CI 的 `postgres` job 里加）。 |

### 8. 密钥投递仍是环境变量

| | |
|---|---|
| **模块** | `docker-compose.yml` · 部署 |
| **表现** | `LAB_JWT_SECRET: ${LAB_JWT_SECRET:?…}` 由 shell 提供；没有 Docker secret / KMS。 |
| **影响** | 密钥会进 shell 历史；轮换没有流程。代码侧已经 fail-closed（缺密钥**拒绝启动**、公开默认密钥也拒绝启动），所以**剩下的只是投递方式**。 |
| **排查/解决** | `docker secret` 或 compose 的 `secrets:` + 文件挂载；轮换时同步失效旧令牌即可（令牌 2 小时过期，窗口小）。 |

### 9. 违约只覆盖「未到场」，且判定准确度没有数据支撑

| | |
|---|---|
| **模块** | `domain/violations.py` · `sweep.py` |
| **表现** | `blocking_enabled=false`（**刻意的上线顺序**：先观察再处罚）。接口只给 `count`（**已豁免的不计入**），看不到「判过几次 / 其中几次被豁免」，也没有判定准确率的任何度量。 |
| **影响** | 处罚开关打开之前，没有人能回答"判定准不准"。控制台昨天补了违约面板（能看到证据并豁免），但准确率仍然要人工统计。 |
| **排查/解决** | 接口加 `no_show_total` / `pardoned_total`（`count_violations` 已有过滤条件，多两个 count 而已）。**更值得注意的是判不了的比例**：`find_no_show_candidates` 已经返回"判不了的数量"，把它接进指标，长期偏高就说明该实验室根本没接门禁 —— 那个数字比任何文档都更早让人发现问题。跑一个学期再决定是否打开处罚。 |

### 10. 清扫跑在服务进程内

| | |
|---|---|
| **模块** | `sweep.py`（lifespan 里起停的循环） |
| **表现** | 任务循环在 API 进程内；多副本时每个副本都会扫一遍。 |
| **影响** | **不会算错**（任务幂等、状态切换都用带条件的 UPDATE + rowcount），只是白花 CPU 与重复归档。 |
| **触发条件** | 与第 5 条同一个触发点（多副本）。 |
| **排查/解决** | 挪成独立 worker / 独立的 compose 服务（`command: python main.py sweep --loop`）；单副本下不必做。 |

## P3

### 11. CLI 在重建 / 恢复库之后打印 `Event loop is closed`

| | |
|---|---|
| **模块** | `cli.py` · `db.py`（`dispose_engine`） |
| **表现** | `main.py seed --force` 与 `main.py restore` 都能复现：命令**成功**（数据正确、恢复后逐表校验通过）、**退出码是 0**，但结尾打一段 `RuntimeError: Event loop is closed` 的 traceback。 |
| **影响** | 运维看到 traceback 会以为失败；脚本里 `grep -i error` 会误报。数据侧没有问题。 |
| **排查/解决** | 根因在**事件循环亲和性**：`migrate()` 用 `asyncio.to_thread(alembic upgrade)`，而 alembic 的 `env.py` 在线程里自己 `asyncio.run()` —— 应用那个 engine 单例的 asyncpg 连接被绑到了那个短命 loop 上，之后在主 loop 里 dispose 就报"attached to a different loop"。方向：命令收尾时**先 dispose 再校验**，或给迁移路径单独用一个短命 engine 并在结束时显式关闭。 |

## 与代码无关的环境 / 运维项

| 项 | 表现 | 处理 |
|---|---|---|
| **运行中的容器是旧镜像** | 本地那个 compose 栈是昨天早先的镜像，**不含**新控制台与备份卷改动 | `docker compose up -d --build` 重建 api 容器即可（命令会让栈短暂中断几秒） |
| **Docker 守护进程写死 `127.0.0.1:7890` 代理** | Clash 一换端口或没开，`docker pull` 立刻失败，报错像"网络问题" | 配 registry mirror（`docker.m.daocloud.io` / `docker.1ms.run` 实测可用），彻底摆脱对代理的依赖 |
| **国内网络拉 Docker Hub 不通** | `registry-1.docker.io` 经代理与直连都是 000 | 同上，配镜像源 |
| **py3.10 job 的 pytest 曾失败一次且机制未知** | 本地用 Python 3.10.21 + 同源依赖（SQLAlchemy 2.0.54）复现不出（整套 exit=0）；之后 5 次运行该 job 全绿 | **已埋伏**：失败时把 `FAILED` 行抬进 CI **注解**（无需鉴权可读）。下次复现先读注解拿用例名，别再花时间本地复现 |

## 建议的处理顺序

**试点开始前**：第 1 条（改期）与第 2 条（门禁开放时间）—— 一条是最高频的不满，一条是安全问题。
**顺手做掉**：第 3 条（错误响应带 reason）与第 4 条的 ②③（通知的全系统视图与截断告知）—— 都是几行的改动。
**试点期间观察**：第 9 条（违约判定的准确率）。
**触发才做**：第 5、6、7、10 条。
**明确不做**：第 17、18 条。
