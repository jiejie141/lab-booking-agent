> 评估基准：`lab-booking-agent` @ `b132bbf`（Python 3.13.14，FastAPI + LangGraph）
> 评估方式：读代码 + 跑实验。**下文每条局限性都附复现方式或代码位置**，
> 不做「一般来说企业级需要……」式的泛泛而谈。

## 结论摘要

| 问题 | 结论 |
|---|---|
| 技术栈完整吗？ | **AI 应用层完整且主流；企业级服务层基本缺位。** 像一个「技术选型全部正确、但只搭到应用层的单机原型」 |
| 是主流方案吗？ | **核心选型没有过时项**。FastAPI / LangGraph / SQLAlchemy 2.0 async / pydantic v2 / pytest 都是当前主流；两处刻意非主流（手写 BM25、零依赖单页控制台）是设计取舍，不是技术债 |

### 与原方案的差异（为什么没照抄）

- **P0-2 不引 `pyjwt` / `passlib[bcrypt]`，改用标准库自实现。**
  `hashlib.scrypt` + 手写 HS256（就是 `base64url(hmac-sha256(...))`，无算法复杂度）。
  理由有三条：bcrypt 在 Windows 上要 MSVC 工具链才能装；少两个依赖就少两条供应链；
  而这两个函数的边界很清楚，接口刻意与 pyjwt 对齐（`create_access_token` /
  `decode_access_token`），日后要换成成熟库只是替换两个函数体。
  **代价**：自实现意味着要自己把安全细节补全，已覆盖强制 `alg == HS256`（挡 `alg=none`）、
  `hmac.compare_digest` 比对（时序安全）、`exp` 缺失即拒（不签「永久凭证」）、
  未知账号与错口令返回**完全相同**的 401（防账号枚举）。
- **P0-3 不引 `slowapi`，用进程内滑动窗口。** 按**用户**而非按 IP 限流 ——
  校园网出口 IP 天然共享，按 IP 会让同校用户互相误伤。
  **代价已写进 README「已知限制」**：单进程、重启清零、多副本下等于配额乘以副本数，
  生产要换 Redis 计数器。这个取舍是故意的 —— 与其上一个要引 Redis 的「假完整」，
  不如把边界写清楚。
- **P0-1 只做了方案 B（占用表），没上方案 A（PG `btree_gist` 排他约束）。**
  A 只能在 PostgreSQL 上跑，本地开发与 CI 都验证不到。B 是「任何重叠都必然撞唯一索引」，
  与数据库无关，可移植且可测试。`acquire_equipment_lock` 保留但**改掉了误导性注释**：
  它现在是显式的性能优化（PG 下按设备做事务级串行），并注明**不承担正确性职责**。

| 能力面 | 现状 | 缺什么 |
|---|---|---|

### 1.3 判断

**这套栈的问题不是「选错了」，而是「只搭了一半」。**
应用层的每一块（Web 框架、编排、ORM、校验、测试）都选得对且不过时；
但「一个服务要长期跑在生产上所需要的那些东西」，几乎全空。

一句话定位：**它现在是一个技术选型正确的单机应用，不是一个服务系统。**

## 二、局限性（按严重度排序，带实证）

### 2.1 【严重·数据正确性】非重叠不变式没落到数据库层，可复现超卖

这是全项目最严重的问题，因为它是**静默的**：接口返回成功、测试全绿、日志正常，
但库里躺着两条互相重叠的有效预约。

**根因**——`models.py` 的部分唯一索引建在三个列上：

```python
Index("uq_res_active_slot", "equipment_id", "date", "start_time", unique=True,
      sqlite_where=text("status IN ('pending','confirmed')"), ...)
```

它只能拦住**开始时间完全相同**的写入。而真正的业务不变式是「时间区间不重叠」——
`13:00-15:00` 与 `14:00-16:00` 开始时间不同，索引看不见。

按 `booking.py` 的设计，这种情况本该由第二层防线兜住：
`acquire_equipment_lock()` 加设备级锁 + 锁内复检。**但它在 SQLite 上直接返回、什么也不做**：

```python
if dialect == "sqlite":
    return "sqlite_write_lock"      # ← 不加锁，注释说"写事务天然互斥"
```

SQLite 的写事务确实互斥，**但这不构成保护**：两个事务可以各自先 `SELECT` 读到「无冲突」
（读快照），再先后写入。互斥只保证了「不会同时写」，没保证「不会分别写成功」——
于是 check-then-act 的窗口依然敞开。

**复现**（脚本已入库）：

```bash
python scripts/overlap_race.py
```

```
【同开始时间（对照组）】20 并发 · 请求 09:00-11:00
  成功 1 · 落库 1 条          ✓ 恰好 1 条
【部分重叠·不同开始】20 并发 · 请求 13:00-15:00, 14:00-16:00
  成功 2 · 落库 2 条          ✗ 超卖
【完全包含关系】20 并发 · 请求 15:00-17:00, 15:30-16:00
  成功 2 · 落库 2 条          ✗ 超卖
结果：1/3 项通过
```

**为什么现有的并发压测没发现**：`main.py loadtest` 的 40 个并发用的是**同一个开始时间**，
恰好走在唯一索引能覆盖的路径上。**「并发安全」这个结论此前只在一种情形下成立，
却被当成了普遍结论** —— 这比 bug 本身更值得记。

**影响面**：README、代码注释、简历都会写「并发安全由数据库唯一索引兜底」。
一旦面试官追问一句「两个时段部分重叠呢」，整条叙事会当场崩掉。

---

### 2.2 【严重·安全】没有认证与授权，身份来自请求体

| 位置 | 问题 |
|---|---|
| `schemas.ChatRequest` | `user_id: int = 1` —— 身份是**请求体里的一个整数**，默认还是管理员以外的 1 号 |
| `api.reservations` | `user_id=None` 时**返回全库所有预约**（含他人姓名、用途、时段） |
| `api.cancel` | `user_id` 同样来自请求体；只要知道对方 user_id 就能替他取消（`cancel_reservation` 里唯一的鉴权就是比对这两个都来自请求体的值，等于没鉴权） |
| 全站 | 无 token、无 session、无 API key；`/api/agent/chat` 无限流，等于开放模型算力入口 |

风险等级：这是**越权 + 数据泄露 + 资源滥用**三合一。
对演示无所谓，对任何真实环境都是阻断级缺陷。

---

### 2.3 【中·可扩展】状态与算力绑死在单进程上

- **会话在内存**：`SessionStore` 是模块级单例，进程重启即丢；多副本部署时
  「第 2 个」会漂到另一台机器上找不到。已经装了 `langgraph-checkpoint` 却没接。
- **检索器每次请求重建**：`api.retrieve` 里 `build_retriever(...)` 是**每个请求**都建一次索引。
- **无分页**：`list_reservations` 全量返回，数据一多就是内存与带宽事故。
- **长请求同步阻塞**：真实模型下 `/api/agent/chat` 是 5–30 秒的长请求，
  占着 worker 不放，没有队列化 / 202 / SSE。
- **单 worker**：`uvicorn.run(...)` 单进程，无法吃满多核。

### 2.4 【中·可观测】只有节点级 trace，没有运行时可观测性

自研 trace 解决的是「这一次对话走了哪些节点」，解决不了：
无结构化日志（无法按 request_id 串起来）、无指标（不知道 p95、错误率、QPS）、
无追踪（跨服务断链）、无告警。出问题只能靠翻 stdout。

### 2.5 【中·数据生命周期】没有迁移能力与治理

`create_all()` 建表意味着**schema 一旦需要变更就只能删库重建**。
更麻烦的是它的语义容易被误解为「自动跟进 schema」：它**只创建缺失的表，从不演进已有的表**，
所以旧库会静默停在老结构上，直到某条业务路径撞上缺列才报错 —— 而没走到那一步的路径
（比如不查 `users` 的寒暄）完全正常，表现为「部分可用」这种最难排查的形态。

当前项目已经在 `ensure_schema()` 里把这件事**在边界上一次性检查掉**（启动 / `doctor` /
种子三条路径共用），过期就明确拒绝启动并给出可照做的修法；`doctor` 把它列成检查项
而不是自己崩掉。但这只是**检测 + 重建**，不是迁移：没有版本表、没有增量脚本、
没有回滚、重建必然丢数据。真正的迁移能力（Alembic）是本节的 P1 第一项。

加上没有保留策略、没有备份、没有软删除、没有独立审计表
（现在只有 `created_at/updated_at/cancel_reason`，答不出「谁在何时改了什么」）。

### 2.6 【中·AI 工程】评测与成本两条线都是空的

- **评测只覆盖 mock 模型**：14/14 是确定性假模型的成绩，**不能外推到真实模型**。
  README 已如实标注，但这仍意味着「真实模型准确率」是一个空值。
- **无成本核算**：不知道一次会话烧多少 token、多少钱。
- **无模型降级链**：只有一个端点，挂了就从「Agent」掉到「引导式表单」，中间没有兜底模型。
- **无输出 schema 校验**：已有「事实由代码给、模型只负责措辞」的约束，
  但对模型输出没有强制 schema + 失败重试。
- **无 prompt 版本管理**：prompt 硬编码在代码里，改了就没了对照。

### 2.7 【轻·交付工程】没有流水线

无 CI、无 lint/format（ruff/black 未引入）、无类型检查（有完整类型标注但 mypy 未接入——
等于标注白写）、`requirements.txt` 是范围约束**不是锁**、`docker-compose.yml` 未实机验证、
API 无版本化。

## 三、升级方案

**分期原则**：每期都有**可演示的验收标准**，且不引入当前用不上的组件。
P0 不装任何新中间件就能做完——它全是「把已有的说法补成真的」。

### P0 · 正确性与安全底线（必做，性价比最高）

> **实施状态：三项均已完成**（`7000e0b` / `9c8207f` / `33da4c8`），
> 差异与验收证据见上方 §实施进度。

#### P0-1 把「区间不重叠」真正下沉到数据库

两条路线，建议 **B 为主 + A 为增强**：

| | 方案 A：PG 排他约束 | 方案 B：时段占用表（推荐） |
|---|---|---|
| 做法 | `btree_gist` + `EXCLUDE USING gist (equipment_id WITH =, tsrange(start,end) WITH &&) WHERE (status IN ('pending','confirmed'))` | 新增 `reservation_slots(equipment_id, date, slot_index)`，按 `slot_granularity_minutes`（已有配置，30 分钟）把一条预约展开成若干个块；唯一索引打 `(equipment_id, date, slot_index)` |
| 效果 | 一次到位，数据库层彻底闭死 | **任何重叠都必然撞唯一索引**，与数据库无关 |
| 代价 | 仅 PG；SQLite 下没有等价物（本地跑不了） | 需要多一张表 + 下单时写入占位、取消时释放；占用块数 = 时长/粒度 |
| 取舍 | 生产最优 | 可移植、可测试、**且严格延续「靠索引兜底」的项目叙事** |

配套：把 `acquire_equipment_lock` 从「SQLite 直接跳过」改成**显式记录策略并注释清楚
它不提供重叠保护**（或直接删掉，避免给人「已经保护好了」的错觉）。

**验收**：`scripts/overlap_race.py` 三项全部「恰好 1 条」，
并把它改写成一条 `pytest` 断言（现在的红是证据，修完是回归）。
`main.py loadtest` 增加「混合开始时间」的轮次。

#### P0-2 认证与授权

- **JWT Bearer 认证**（`python-jose` / `pyjwt` + `passlib[bcrypt]`），
  或直接接 OIDC（学校统一认证）——对校内场景更真实。
- **`user_id` 一律从 token 取，从请求体里彻底删掉**（这是本次改动最关键的一条）。
- **RBAC**：`ROLE_USER / ROLE_ADMIN / ROLE_SYSADMIN` 已定义，接上依赖注入做鉴权；
  `GET /api/reservations` 默认只返回自己，管理员才可全量（且要留痕）。
- **验收**：不带 token 的写操作返回 401；A 用户读不到 B 用户的预约；
  普通用户调用管理端点返回 403。

#### P0-3 边界加固

- 限流：`slowapi` 或网关层，`/api/agent/chat` 按用户维度限流（同时守住成本）
- CORS 白名单、请求体大小上限、输入长度与枚举白名单（现在 `purpose` 无长度限制）
- **审计日志**：谁、何时、对哪个资源、做了什么、结果。独立 `audit_log` 表，只追加不修改
- 密钥：`.env` → 密钥管理（PG 部署下至少 Docker secrets / 云 KMS）

**验收**：一份最小渗透清单跑通（越权读/越权改/无 token 写/超大 body/高频刷接口）。

### P1 · 生产就绪

| 模块 | 技术组件 | 目标 |
|---|---|---|
| Schema 迁移 | **Alembic** | `create_all` 退役；变更可回滚 |
| 会话持久化 | **LangGraph checkpointer**（`AsyncPostgresSaver` / `SqliteSaver`） | 替换 `SessionStore`，多副本无状态 |
| 缓存 | 进程内 LRU（单副本）→ **Redis**（多副本） | 设备目录 / 实验室 / 检索器单例化 |
| 可观测 | **structlog**（JSON 日志）+ **prometheus-fastapi-instrumentator** + **OpenTelemetry** | request_id 贯穿；自研 trace 作为 span 上报；`/metrics` 出 p95/错误率 |
| 长任务 | **ARQ / Celery / Dramatiq** 或 FastAPI 的 `BackgroundTasks` + 轮询 | 模型调用异步化，返回 202 + task_id |
| API 治理 | 游标分页、过滤、`/api/v1` 前缀、**幂等键**（`Idempotency-Key`） | 重复提交不产生重复预约 |
| 交付 | **ruff + mypy + pytest + docker build** 的 CI；`uv lock` 锁依赖 | 每次提交自动验证 |
| AI 工程 | 真实模型评测集 + token 成本看板 + prompt 版本化（放配置/DB，不硬编码） | 「准确率」与「单次成本」两个数字可引用 |

**验收**：CI 全绿；**跑两个副本 + PostgreSQL，多轮对话不漂移**；
压测的 p95 / 错误率作为基线写进 README。

## 四、目标架构

```
                         ┌──────────────────────────────┐
   浏览器 / 移动端 ──────▶│  Edge：网关 / WAF / 限流      │
                         └──────────────┬───────────────┘
                                        │  JWT
              ┌─────────────────────────▼─────────────────────────┐
              │                  应用服务层                        │
              │  ┌────────────────────┐  ┌──────────────────────┐  │
              │  │ API 服务 (FastAPI) │  │ Agent Runtime        │  │
              │  │ 鉴权 / 校验 / 分页 │  │ (LangGraph + 持久化  │  │
              │  │ 幂等 / 审计        │  │  checkpointer)       │  │
              │  └────────────────────┘  └──────────┬───────────┘  │
              └──────────┬─────────────────────────┬─────────────┘
                         │                         │
        ┌────────────────▼────────┐   ┌────────────▼──────────────┐
        │ 领域服务                 │   │ Model Gateway             │
        │ 可用性判定 / 协商        │   │ 多模型路由 / 降级链        │
        │ 下单（不变式在 DB 层）    │   │ 配额 / 成本核算 / 缓存     │
        └────────┬────────────────┘   └────────────┬──────────────┘
                 │                                 │
     ┌───────────▼──────────┐        ┌─────────────▼─────────────┐
     │ 数据层                │        │ 异步与消息                 │
     │ PostgreSQL（+ RLS）   │        │ 队列 / Worker / 定时任务   │
     │ Redis（会话·缓存）     │        │ 事件总线（通知·门禁·计费）  │
     │ 对象存储（附件/报告）  │        └───────────────────────────┘
     └──────────────────────┘
                 │
     ┌───────────▼────────────────────────────────────────────┐
     │ 观测平面：结构化日志 · 指标 · 分布式追踪 · 告警          │
     │ （贯穿以上每一层，不是旁挂）                             │
     └────────────────────────────────────────────────────────┘
```

**架构目标（可测量的说法）**：

1. **无状态化**：应用副本可任意增减，会话与缓存外置 → 水平扩展
2. **不变式单一来源**：所有正确性约束由数据库保证，应用层只负责给出**可读的拒绝理由**
3. **模型可替换、可降级**：模型是「措辞层」，换模型不改变业务结论；多模型 + 降级链
4. **一切可观测**：任一请求可用 request_id 串起日志/追踪/指标
5. **失败可解释**：任何拒绝都带结构化原因（本项目已有的 `blocker_kind` 应当延续到全系统）

## 五、安全性要求清单

| 类别 | 要求 |
|---|---|
| 身份 | 强制认证；token 短期 + 刷新；`user_id` 只来自 token |
| 授权 | 资源级校验（只能操作自己的预约）；RBAC 覆盖管理端点；**默认拒绝** |
| 输入 | pydantic 严格模式；长度/枚举/范围白名单；拒绝未知字段 |
| 传输 | 全站 TLS；HSTS；CORS 白名单（非 `*`） |
| 滥用 | 按用户/接口限流；模型调用配额；请求体大小上限 |
| 数据 | 最小权限 DB 账号；PII 字段加密或脱敏；备份加密 |
| 审计 | 关键写操作全部留痕，只追加；可导出 |
| 密钥 | 不落代码库；环境变量 → 密钥管理服务 |
| 依赖 | 定期扫描 CVE（`pip-audit`）；锁定版本 |
| 模型 | prompt 注入防护（外部文本不进入指令位）；输出 schema 校验；**不让模型裁决权限**（本项目已做到，应保持） |

## 七、明确「不建议做」的部分

这一节和升级方案一样重要——**过度工程在面试里是负资产**：

- ❌ **不要上 K8s / Service Mesh**。你无法真实运维它，被问「为什么用 K8s、怎么做的灰度」就是灾难。
- ❌ **不要为「显得高级」引 Kafka / Elasticsearch**。当前量级用不上；被问容量估算与成本就露馅。
- ❌ **不要声称支持多租户 / SSO / 高可用**，除非真的跑通过一遍。
- ❌ **不要把 P2 的组件名写进简历**。写了就要能回答三层追问（为什么选它 / 怎么配的 / 出问题怎么排查）。
- ❌ **不要为了「企业级」把项目改成一个自己都讲不清的系统**。
  对这个项目，**P0 做扎实 > P1 做一半 > P2 全写在纸上**。

| 状态 | 可以写的内容 | 追问风险 |
