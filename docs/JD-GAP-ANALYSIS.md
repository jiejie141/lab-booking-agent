# 与「超线性 · AI agent 开发实习」JD 的差距分析与升级方案

> **对象项目**：`lab-booking-agent`（FastAPI + LangGraph 实验室预约 Agent）
> **目标岗位**：深圳超线性科技有限公司「AI agent 开发实习」
> 300–600 元/天 · 深圳南山科技园 · 5 天/周 · 6 个月 · 本科在读
>
> **结论一句话**：当前项目是「**应用层做得非常扎实、Agent 运行时层基本空缺**」的形态，
> 而这家 JD 的重心恰恰在运行时层。差距**不是功能少，是能力层次错位** ——
> 但现有那套工程严谨性（零 `type: ignore`、322 测试、区间不变式下沉、审计与越权防护）
> 恰恰是实习候选人里最罕见的资本。所以升级方向应该是
> **把应用层的严谨性抽成一层可复用的运行时**，而不是推倒重做。

## 〇、先看清这家公司在招什么（这决定了「期望」的真实水位）

> 来源：牛客网公开企业页。属于公开信息摘要，可能不完整或有滞后，面试前建议自行核对官网。

超线性做两个 Agent 产品：

- **Deeplink** —— 帮中国出海企业做**海外网红营销**的 AI Agency
  （客户含国内 TOP3 AIGC 独角兽、Brand Z 中国出海品牌 TOP10、出海 100 强）。
  去掉营销话术，本质是**达人/线索的发现与匹配**。
- **Lessie AI** —— People Search AI Agent，自我定位「AI 时代的 LinkedIn」：
  用**大模型 + 多模态检索**对特定人群做自动搜索、信息提取、**身份验证**，
  再按任务目标**生成沟通策略**，完成「发现—触达—交互」全流程闭环。

**两个产品的 OS 都是 Agent 本身。** 所以 JD 第 3 条
「参与 Agent Harness 运行时框架的开发维护⋯沉淀可复用的 Agent 执行能力」
**不是套话** —— 对这家公司来说，Harness 就是产品的地基。这是理解全部要求的钥匙。

由此有三条推论，会贯穿整份方案：

1. **面试官不会真的关心"你做了个预约系统"，他会关心"你的 Agent 骨架换个业务还能不能跑"。**
2. **「People Search」与「设备预约」在结构上是同构的**（详见 §3.6）：
   模糊需求 → 约束下检索候选 → 不满足时协商/放宽/给替代 → 生成沟通措辞 → 全流程可观测可评测。
   这意味着本项目的**协商引擎可以直接迁移**。这是最大的隐性优势，务必打出去。
3. 加分项 4「B2B、销售线索、企业数据」对应的就是这两个产品。它写的是"优先"不是硬门槛，
   但**它说明面试官会顺口问业务理解，不只问代码**。

## 一、把 JD 拆成可判定的条目

先定义深度标尺，否则"差距"是空话：

| 等级 | 含义 |
|---|---|
| L0 | 完全没接触 |
| L1 | 知道概念，能复述 |
| L2 | 用过，能跑通 |
| L3 | 能独立实现，并讲清设计取舍 |
| L4 | 做过工程约束与权衡，**踩过坑并能说出坑在哪** |
| L5 | 能抽象成框架并沉淀复用（这家 JD 的真实水位） |

| # | JD 原话 | 它真正在考什么 | 本项目现状 | 等级 |
|---|---|---|---|---|
| 职责1 | 后台服务、App 接口的开发/调试/维护 | 能否独立交付可联调的接口 | FastAPI + 40 KB 单文件控制台，8 组端点，真进程冒烟 39/39 | **L3** |
| 职责2 | 大模型编排、**Tool/Function Calling 工具调用**、RAG、向量检索 | 模型侧协议，不是应用侧路由 | 编排 L3；**工具调用 L1（见 §2）**；BM25+RRF L3；**pgvector/Milvus L0** | **L1–L3** |
| 职责3 | **Agent Harness 运行时**：上下文管理、工具加载、多智能体调度 | **能不能造/改运行时** | 上下文 = 一个 `history` 字符串 + 进程内 dict；工具 = 硬编码调用；多智能体 = 无 | **L1 ← 断崖缺口** |
| 职责4 | 迭代重构、性能优化、**评测/日志/监控**、线上稳定 | 生产意识 | 重构 L3；压测 L2；**结构化日志/指标 L0**；降级链 L3 | **L0–L3** |
| 职责5 | 技术文档、代码评审、接口联调 | 协作与表达 | 文档 **L4**（README 踩坑表）；代码评审 L0 | **L0 / L4** |
| 要求2 | Python / FastAPI / MySQL / **Redis / 消息队列** | 后端基本功 | Python+FastAPI L3；裸 SQL 偏弱 L2；**Redis L0；MQ L0** | **L0–L3** |
| 要求3 | OpenAI/Claude API、Prompt、工具调用、对话上下文 | LLM 基础概念 | API L3（httpx 直连、mock/live 双模）；Prompt L2；**上下文 L1** | **L1–L3** |
| 要求4 | **把大模型作为系统组件做工程约束** | —— | 事实由代码给、模型只负责措辞；结构化拒绝原因；模型不可用降级 | **L4 ← 核心资本** |
| 加分1 | LangChain/LangGraph/LlamaIndex 做过 Demo | 编排框架 | LangGraph 7 节点 + 3 条件边 | **L3** |
| 加分2 | RAG、**向量检索（Milvus/pgvector）**、链路追踪 | 检索与可观测 | 手写 BM25 + RRF 融合 L3；chromadb 可选 L2；**pgvector L0**；追踪 L2（自研节点级） | **L0–L3** |
| 加分3 | Docker / K8s / 模型推理部署 | 云原生 | Dockerfile + compose **未实机验证**；K8s L0 | **L1** |
| 加分4 | B2B、销售线索、企业数据 | 业务理解 | 校园实验室预约（域不同，但**结构同构**，见 §3.6） | **L1**（如实讲） |

**读表结论：**

- 硬门槛里的 **Redis 与消息队列是完全空白**，而它们恰好是**一周内最容易补到"能讲清"的**。
- 加分项里 **pgvector / Milvus 空白**且 JD 点名了。补它远比补 K8s 划算 —— K8s 本地都跑不起来，谎报必被追问穿。
- **职责 3 是断崖式缺口**，也是这个岗位区别于"普通 Agent 应用开发"的唯一标志。
- **要求 4 是现有资本**，必须主动打出去。

## 二、关键发现：这个项目的「工具调用」不是工具调用

这是本次逐文件核对里最该先处理的一条，因为它**既是能力缺口，又带着一个很容易踩的表述坑**。

**事实（可核对）**：

- `src/lagent/agent/tools.py` 有一份 `TOOL_SPECS` —— 5 个工具，带 `name` / `description` / 参数说明，
  **看起来像 function calling 的 schema**；
- 但 `src/lagent/agent/llm.py` 调用模型时只传 `response_format={"type": "json_object"}`，
  **从未传 `tools` 或 `tool_choice`**；
- `graph.py` 的节点是**直接** `await tool_query_availability(...)`，
  路由由 `_after_parse` / `_after_ask` 这些**条件边**按意图决定。

**结论**：模型**从来没有选择过工具**。这是一套**确定性工作流（deterministic orchestration）**，
不是 tool calling。`TOOL_SPECS` 目前只是一份清单/文档。

**为什么这是风险（这里要说准确，别夸大）**：

README 与 `doctor` 输出里的「已注册工具：query_availability, ⋯」这句话
**本身没有说错** —— 它们确实是注册在 `TOOL_SPECS` 里的工具，
只是由条件边调用、而非由模型选择。（实测 `grep -n "工具" README.md` 只有两处命中，
都不含"由模型调用"这层暗示。）

风险不在文档撒谎，在于**「已注册工具」这四个字极易被读成 function calling**：
面试官顺着这个词往下问、或者你顺着这个词往下讲，就会讲到一个代码不支持的地方去，
**然后被 `llm.py` 反证**。这是"表述歧义"型风险 —— 比虚假陈述轻，但发生的概率更高。

所以处理成本很低：**加一句主动划清界限的说明**即可（见阶段 A），不需要重写文档。
而且主动说清"我的路由是确定性的、function calling 在做"，
**比含糊过去更像懂行的人** —— 它证明你知道这两者的区别。

> **本节描述的缺口已于 `ff747ff` 补上，上面这段保留下来当"起点"看。**
>
> 现在的事实变了，可核对：
>
> - `src/lagent/agent/llm.py` 的 `chat_tools()` 在 live 模式下**真的传了
>   `tools` 与 `tool_choice="auto"`**，并把 `tool_calls[].function.arguments`
>   解析回结构化参数（含"模型给了非法 JSON"的处理：不抛错，给空 dict，
>   由参数校验那一关回喂"缺哪个字段"）；
> - 工具选择权真的交给了模型：`ReActRuntime.run()` 是
>   `think → tool_call → tool_result → … → final` 的循环，
>   由模型决定调哪个工具、什么时候停；
> - 原来的确定性路径**没有被删掉**，而是变成 `LAB_EXECUTION_MODE=deterministic`
>   （默认）下的另一种执行模式。
>
> **所以本文开头那条"工具调用不是工具调用"的结论，对 deterministic 模式仍然成立，
> 对 react 模式已经不成立。** 讲的时候要按模式区分，别一句话概括两种模式。
>
> 仍然成立的部分（别一起改掉）：`tool_selection` 的质量数据依旧没有 ——
> 见 §4 的进度表。

**但这里有一个反转，讲好了是加分项。** 这是整份方案里性价比最高的一段话：

> 「我的路由是**故意**确定性的 —— 预约是强约束业务，让模型自由选工具有幻觉风险：
> 它可能该查可用性却直接下单。所以我把高风险动作收敛成确定性编排。
> 但我在升级时做了**两条执行路径**（模型自主决策 / 确定性编排），
> 因为通用 Agent 场景下必须让模型自己选工具 —— 这两条路径的取舍，我用评测量过工具选择正确率。」

这段话同时命中：要求 4（工程约束）、职责 2（工具调用）、职责 3（运行时抽象）、职责 4（评测）。
**它把一个"谎言风险"直接转成了一个"设计取舍"。**

## 三、六个维度的目标

### 3.1 技术深度

目标：把 JD 里出现的每个词，从"用过"推进到"能讲清取舍、踩过坑"。

| 主题 | 现状 | 目标 | 必须能回答的追问 |
|---|---|---|---|
| **工具调用** | 条件边硬编码 | 原生 `tools`/`tool_choice` + 参数 schema 校验 + 非法参数回喂重试 + 工具结果超长截断 | 为什么用 function calling 而不是在 prompt 里塞 JSON？`tool_choice` 什么时候强制、什么时候 auto？并行工具调用怎么处理与落库？ |
| **上下文管理** | 一个 `history` 字符串 | 分层（system / 长期记忆 / 近轮 / 工具结果）+ token 预算 + 超限策略（丢工具结果 → 摘要近轮 → 截断） | 32 k 上下文塞满时你先丢什么、保什么、为什么？摘要用什么模型、代价多少？ |
| **向量检索** | 手写 BM25，语料仅 ~10 chunk | 真 embedding + pgvector + 分块策略 + 混合检索 + **检索质量评测（recall@k / MRR）** | chunk 切多大、为什么？两路融合的权重怎么定的？向量在你这个场景真的比 BM25 好吗（拿数字说）？ |
| **Harness** | 无 | 见 §3.4 | LangGraph 给了什么、没给什么？你为什么还要在上面补一层？ |
| **可观测** | 自研节点级 trace | span 化 + JSON 日志 + `/metrics` | 线上一次慢请求，你从哪三个地方看出来它慢在哪？ |

### 3.2 功能完整度

目标是**覆盖 JD 五条职责的闭环**，而不是堆功能：

- **职责 1**（后台服务/App 接口）：补 `/api/v1` 前缀、游标分页、幂等键、OpenAPI 契约；
  以及**接口联调的物证**（`scripts/` 下一个 httpx 端到端脚本，比"我用 Postman 调过"强）。
- **职责 2**：见 §3.1。
- **职责 3**：`harness/` 从 0 建 —— 这是必须做的那一件。
- **职责 4**：Redis / 消息队列 / 结构化日志 / metrics / 真实模型评测 + 成本核算。
- **职责 5**：文档**已是强项**。补 `CONTRIBUTING.md` + PR 模板 + **一次真实的 PR review 记录**
  （哪怕是自审一个 feature 分支，把评论写进 PR —— 面试官看的是"你会不会提有效意见"）。

### 3.3 代码质量

现状其实已经在 L4（这在实习候选人里很少见）。目标不是提分，是**把证据做成一眼可见**：

- **保持并主动展示**：`ruff` + `mypy`（43 源文件、**零 `type: ignore`**）+ **322 测试** + CI 三 job
  （quality / smoke / docker 按失败信号拆开）。
  ⚠️ 零 `type: ignore` 这条**要在面试时主动讲** —— 因为它可以当场 `grep` 验证，是最硬的可信度信号。
- 补：覆盖率门禁（`--cov-fail-under`）、`uv lock` 锁依赖（现在 `requirements.txt` 只是范围约束）。
- 补：**分层边界检查**（`import-linter` 或 ruff 的 `TID` 规则），证明"分层清晰"不是嘴上说的 ——
  业务层不许 import 基础设施层，这条能自动化验证。

### 3.4 架构设计

现状：分层清楚（`api` / `agent` / `domain` / 数据），但**运行时与业务是耦合的** ——
上下文管理写在 `graph.py` 的节点里，工具协议不在任何地方，执行模式写死成一种。

**目标架构（本 JD 的决胜点）**：

```
业务层 —— 本项目的护城河，语义不动
  domain/  negotiate（协商）· booking（落库）· availability（窗口）
  工具实现  5 个 tool_*（业务语义）
        │  只依赖 harness 暴露的接口
────────┼──────────────────────────────────────────────────────────
Harness 运行时层 —— 新建，本 JD 的决胜点
  context.py   上下文组装：分层 · token 预算 · 超限策略（截断/摘要/丢工具结果）
  tools.py     工具注册表：schema 校验 · 动态加载 · 结果超长截断 · 错误归一
  runtime.py   执行模式：deterministic │ react（模型选工具）│ multi-agent
  trace.py     span 化埋点：每次 LLM 调用 / 工具调用 / 决策 → 可导出 OTel
        │
────────┼──────────────────────────────────────────────────────────
基础设施层
  LLM 客户端（mock / live 双模，OpenAI 兼容）
  持久化：PostgreSQL(+pgvector) · Redis(会话/限流/缓存) · Alembic(迁移)
  异步：ARQ / Celery（模型调用异步化 → 202 + task_id）
  可观测：structlog JSON · Prometheus /metrics · OpenTelemetry
```

**必须能讲的架构取舍**（这是区分 L3 和 L5 的地方）：

> 「为什么不用 LangChain 的 `AgentExecutor`、或者 LangGraph 的 prebuilt ReAct？
> 因为 JD 要的是**沉淀可复用的执行能力** —— 而这两者都把**上下文管理留给了使用者**。
> 我需要知道上下文是怎么被裁的、工具是怎么被加载和校验的，所以这层我自己写。
> LangGraph 我用在它真正强的地方：持久化执行 + 中断恢复（checkpointer）、以及人工介入（HITL）。」

### 3.5 性能与可扩展性

现状：单进程；会话在内存（`SessionStore`）、限流在内存、无缓存、无异步任务。

| 项 | 现状 | 目标 | 验收 |
|---|---|---|---|
| 会话状态 | 进程内 dict | **Redis**（替换 `SessionStore`） | 跑两个副本，多轮对话不漂移 |
| 限流 | 进程内滑动窗口 | **Redis 计数器，用 Lua 保证原子性** | 两副本下配额不被乘 2 |
| 缓存 | 无（检索器每请求重建） | Redis 缓存设备目录 / 实验室 / 检索器单例 | 单请求不再重建索引 |
| 长任务 | 同步阻塞在请求里 | **MQ**（ARQ/Celery）+ 202 + task_id + SSE/轮询 | 模型慢时接口不超时 |
| Schema | ~~`create_all`~~ → **Alembic 已落地**（`migrations/`，`0001` 覆盖全部 10 张表） | ✅ 完成 | 变更可回滚；CI 断言「迁移产物 vs 模型 diff 为空」 |
| 基线 | 无 | 压测出 p95 / 错误率写进 README | 有数字可引用 |

⚠️ **口径要守住**：单机 40 并发**不是高并发**。这里的价值是
「**区间不重叠不变式的正确性验证**」，不是性能数字。说成高并发会被追问穿。

### 3.6 业务认知（加分项 4 的补法）

业务域（出海营销 / 销售线索）**补不动** —— 你没有那个经验，硬编会被问穿。
但**结构可以迁移**，而这家公司的产品恰好和你的骨架同构：

| Lessie AI / Deeplink 在做的事 | 你项目里已经有的对应物 |
|---|---|
| 用户给一个模糊需求（"找能做 XX 的海外 KOL"） | 「明天下午想用荧光光谱仪两小时」 |
| 在**约束**下检索候选（粉丝量/地域/报价/合规） | 资质 / 时段 / 容量约束下检索可用时段 |
| 不满足时说**为什么**（硬条件不满足 ≠ 候选没档期） | `blocker_kind`：`no_target` / `constraint` / `no_date` |
| 不可满足时给**放宽方案**并说明放宽了什么 | `Proposal.relaxations` + 阶梯放宽 + 接近度打分 |
| 生成**沟通策略/话术** | `compose` 节点（模型只负责措辞，事实由代码给） |
| 「发现—触达—交互」全流程要可观测、可降级 | 节点级 trace + 三档降级链 |

**这段话这么说**（诚实版）：

> 「我的选题是实验室设备预约，不是销售线索 —— 这点我如实讲。
> 但我发现这两个问题在结构上是同一个：**模糊需求 + 强约束下的候选匹配 + 不可满足时协商**。
> 所以我升级时会刻意把协商引擎从业务语义里抽出来 —— 它应该能直接换到'按需求匹配人'的场景上。
> 换句话说，我练的是骨架，不是那个外壳。」

`tools` 参数、真的自己选工具、真的会被护栏拦下写操作），但这一阶段当初定的验收是

**证明不了工具选择的质量**。要补这一项，需要真实端点 + 一档新的评测维度。

### 阶段 A｜划清界限与对齐口径（0.5 天）—— 先做，因为它成本最低、收益最直接

不是"改掉错误表述"（文档并没有错，见 §2），而是**主动消除歧义**：

- 在 README 的 `main.py tools` 那行、以及「架构」表里 `agent/` 那行的描述后面，
  各补一句：**「当前为确定性编排：工具由条件边按意图路由，不是由模型选择；
  function calling 见 docs/JD-GAP-ANALYSIS.md 的阶段 B」**。
- 同步修正 `doctor` 输出里 `已注册工具` 那行的标签，改成
  `工具（确定性路由）`，让自检输出本身就说清机制。
- **验收**：把 README 通读一遍，**任何一句都不会被代码反证**；
  且"确定性编排 vs function calling"的区别在不看代码时就已说明白。

### 阶段 B｜让模型真正拥有决策权（3–4 天）

- `llm.py` 接入 `tools` / `tool_choice`；live 模式下跑 **ReAct 循环**（think → tool_call → tool_result → think → final）。
- 工具参数用 pydantic schema 校验；**非法参数回喂模型重试，而不是抛异常**。
- 工具结果超长截断（这是上下文管理的第一课，顺手做了）。
- **保护栏**：`create_reservation` / `cancel_reservation` 这类有副作用的高风险工具，
  强制走确定性路径或要求显式确认 —— 不允许模型自由触发。
- 评测新增一档 `tool_selection`（工具选对没、参数对不对），与现有三档（intent/slots/e2e）并列。
- **验收**：live 模式能跑出 `tool_selection` 数字；**mock 模式确定性路径仍 14/14（不允许回退）**。

### 阶段 C｜抽出 Harness 层（5–7 天）—— **本 JD 的决胜点**

- 新建 `src/lagent/harness/`：`context.py` / `tools.py` / `runtime.py` / `trace.py`。
- 业务层 `domain/` 与 `tool_*` 实现**语义不动**，只改成向 harness 注册。
- 两种执行模式共存、配置切换；降级链：`react → deterministic → 引导式表单`。
- `context.py` 必须真的做预算与分层 —— **要能讲清"超限时先丢什么"**，不能只是拼字符串。
- **验收**：
  1. 新增一个"hello world 工具"只需注册、不需要改 harness（证明可插拔）；
  2. harness 单测覆盖注册表 / schema 校验 / 预算裁剪 / 降级切换；
  3. 业务层不再直接依赖 LLM 客户端（分层边界可自动校验）。

### 阶段 D｜补齐 JD 点名的基础设施（5–7 天）

- **Redis**：会话（替换 `SessionStore`）+ 限流计数器（**Lua 保证原子性**）+ 目录缓存。
- **消息队列**：模型调用异步化（`202 + task_id` + SSE/轮询）。
- **可观测**：`structlog` JSON 日志（request_id 贯穿）+ Prometheus `/metrics` + 自研 trace 转 OTel span。
- **pgvector**：真 embedding 向量检索 + 混合检索，**并补检索质量评测（recall@k / MRR）**
  —— 有数字的 RAG 和"我用了 RAG"是两个层次。
- **Alembic**：✅ 已落地 —— 替换了 `create_all`，正好接上刚修的那条 schema 漂移。
  老库有两条出路（结构与代码一致 → `stamp head` 接管；不一致 → 明确要求重建），
  这条边界值得单独讲，因为它回答的是「你怎么处理存量数据」。**其余四项仍未做**。
- **验收**：**跑两个副本 + PostgreSQL，多轮对话不漂移**；压测 p95 与错误率基线写进 README。

### 阶段 E｜多智能体调度 + 真模型评测（3–5 天）—— 加分与差异化

- 多智能体：协调者 + 可用性专家 + 资质专家 + 规范检索专家，**复用同一套 harness**
  （这也是对 §3.4 那句"沉淀可复用"的实证）。
- 真模型评测：真实 API 跑同一套用例 + token 成本核算 → 产出「准确率」与「单次成本」两个数字。
- **验收**：多智能体相比单体，收益与成本**都有数字**。
  ⚠️ **如果没有收益就如实写"不值得做"，并说明原因** —— 这本身就是 L5 的信号，
  比硬吹多智能体安全得多。

**总计约 3–4 周。**

**如果只有一周**：只做 **A + B + C 里的 `context.py` / `tools.py`**。
理由：**「工具调用」与「上下文管理」是这份 JD 出现频率最高的两个词**，
而多智能体、K8s、消息队列都只是加分项。

## 五、升级后的核心功能与技术亮点

给面试官讲的清单。**每条都必须能指到具体代码**：

1. **可插拔的 Agent Harness** —— 业务只注册工具与策略；上下文、工具协议、执行模式、埋点全在运行时层。
   新增一个业务域**不改运行时**。
2. **双执行模式 + 三档降级链** —— 模型自主决策 ⇄ 确定性编排，模型不可用时降级到引导式表单；
   降级原因**结构化**（沿用具现有的 `degraded` 字段），不静默。
3. **上下文预算管理** —— 分层 + token 预算 + 超限策略，且策略**有测试钉住**（这是"真的做过"和"听说过"的分界）。
4. **真 function calling + 参数校验 + 重试** —— 非法参数回喂模型而非抛异常；高风险工具强制确认。
5. **约束协商引擎（现有资产 + 泛化）** —— 阶梯放宽 + 接近度打分 + 多样性截断 + 结构化 `blocker_kind`。
   **这是可迁移到 People Search / 线索匹配的核心算法，也是你最该讲的一段。**
6. **混合检索 + 检索质量评测** —— BM25 + pgvector + RRF，并给出 recall@k / MRR 数字。
7. **可观测与评测闭环** —— trace span 化 → OTel；评测四档（intent/slots/e2e/tool_selection）；
   真实模型的准确率与单次成本。
8. **工程严谨性（现有的，务必主动打）** —— ruff + mypy（43 文件、**零 `type: ignore`**）+ 322 测试
   + CI 三 job + 区间不重叠下沉到 DB + JWT/RBAC + 审计 + 结构漂移 fail-closed。
   **这套东西在实习候选人里极少见，它比任何花哨功能都更能证明"能带**。
