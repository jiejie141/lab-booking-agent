# 第 1 章 项目全景

## 1.1 系统做什么

实验室的设备（光谱仪、离心机等）需要预约使用。系统提供一个对话式入口：

```
用户：我想明天下午约两个小时荧光光谱仪
      ↓
Agent：解析意图 → 抽槽位（日期/时间/时长/设备）→ 查可用性 → 校验资质与冲突
      ↓
Agent：明天 14:00-16:00 有空，但你没有光谱仪的准入资质，需要先通过培训。要我给你两个替代时段吗？
```

**关键设计判断**：这不是一个「聊天机器人」，而是一个**带自然语言入口的业务系统**。
预约能不能成，由**规则**决定，不由模型决定。

## 1.3 一次「我想明天下午约两小时光谱仪」的完整链路

**这一节要能背下来，面试第一条就考这个。**

```
① HTTP 请求进来
   → 生成 / 透传 request_id（白名单过滤，防日志注入）
   → 认证：解 JWT，校验 token_version
   → 限流：滑动窗口，超了返回 429
   → 幂等：带了 idempotency_key 就先查表，命中直接回放上次结果

② LangGraph 图开始跑，入口节点 parse
   → 先看有没有「点选上一轮备选」（第 2 个）、有没有显式 accept 字段
   → 都没有才调模型：classify_intent + extract_requirement
   → 得到 Requirement{date, start, end, duration, equipment_name}

③ 条件边决定下一站（_after_parse）
   → 意图是取消 → cancel
   → 意图是问规范（需要什么资质） → retrieve
   → 槽位不全 → ask（追问后 END，等用户下一轮）
   → 正常预约 → negotiate

④ negotiate 节点
   → 查该时段活跃预约 → 算冲突
   → 查用户资质（access.py）→ 没资质记 blocker
   → 算备选方案 proposals
   → 可能顺带调 retrieve 拿规范引用，附在回复里（citations）

⑤ book 节点（只有 satisfied 才真的下单）
   → 写库：唯一索引 / 乐观锁保证不会被并发挤掉

⑥ compose 节点
   → 把结构化事实措辞成自然语言（模型唯一负责的「表达」环节）
   → 模型不可用 → 用模板拼一段 DEGRADED_REPLY

⑦ 响应
   → trace 里每一步的耗时与摘要（因为 state 里 trace 是 Annotated 累加）
   → 审计表写一条
```

## 1.4 两种执行模式 + 三档降级（这是最能加分的设计）★

```
react（模型选工具）
   ↓ 模型故障 / 步数耗尽 / 不按格式回
deterministic（代码选工具，显式图路由）
   ↓ 模型显式关闭
引导式表单（前端兜底）
```

**为什么默认走 deterministic**：
> 对预约系统来说，业务规则是明确的 —— 取消意图绝不该被路由到下单工具，「有没有资质」更不允许由模型裁决。把工具选择交给模型只增加不确定性，换来的灵活性在这条业务上用不上。

**但为什么还要保留 react**：
> 「在这条业务上不需要」不等于「不该有」。通用 Agent 场景（模糊需求下自己摸索该查什么）必须让模型选工具，那正是 JD 里 Tool Calling 的含义。所以做成可配置的执行策略，两条路径**共用同一份工具注册表**。

**这句话可以直接背**：
> 模型负责理解语言，代码负责执行规则 —— 而「谁来选工具」是一个可配置的执行策略，不是世界观。

**降级链的诚实边界（这句话很值钱）**：
> 这条链只覆盖「模型还在、只是不肯好好调工具」。模型端点连不上的情况它救不回来 —— 因为确定性路径同样依赖模型做意图识别和槽位抽取。那种情况下的契约是接口明确返回 502 + 前端切引导式表单。把所有故障都声称能兜住是不诚实的。

# 第 2 章 Python 语言特性

## 2.1 类型标注与 Protocol

**为什么用 Protocol 而不是抽象基类**：Protocol 是**结构化类型**（鸭子类型的静态版），
类不需要显式继承就能满足协议 —— 这对「Mock 客户端和真客户端可以互换」这件事是关键：

```python
class LLMClient(Protocol):
    name: str
    async def classify_intent(self, message: str) -> IntentResult: ...
    async def extract_requirement(self, message: str) -> Requirement: ...
```

`MockLLMClient` 和 `RealLLMClient` 都没写 `(LLMClient)`，但 mypy 都能验过。

**代码里记的一个真实坑**（面试可以讲，说明真的踩过）：
> 我本来写了个 `@_measured(op)` 装饰器给 5 个方法加埋点，很干净。挂上去之后 mypy 立刻报错：`RealLLMClient` 不再满足 `LLMClient` 协议 —— `functools.wraps` + `ParamSpec` 装饰出来的方法，mypy 没法再和 Protocol 里那行签名对上。所以退回最直白的写法，在方法体里 `async with track_llm_call(op)` 包住。代价是多一层缩进，换来的是类型契约完整。

## 2.2 TypedDict 与 Annotated

Agent 的图状态用 `TypedDict`（见 `state.py` 的 `AgentState`）：

```python
class AgentState(TypedDict, total=False):
    message: str
    intent: str
    requirement: Requirement
    trace: Annotated[list[TraceStep], operator.add]  # ★ 累加，不是覆盖
```

**`Annotated[..., operator.add]` 这一行是全项目最隐蔽的坑**：
> LangGraph 的默认合并策略是「同名键后写覆盖前写」。如果只写成 `trace: list[TraceStep]`，每个节点返回的都会把前一个节点的记录冲掉，最后只留最后一步。这个坑很隐蔽 —— 图能跑通、结果也对，只是可观测性静默丢失。

**面试可以说**：这就是「功能对但有 bug」的典型，测试如果只断言最终回复，永远抓不到。

## 2.3 dataclass

```python
@dataclass(frozen=True)
class Chunk:
    source: str
    heading: str
    text: str

    @property
    def fingerprint(self) -> str: ...   # 内容指纹
```

**`frozen=True` 的作用**：不可变 + 自动 `__hash__`，可以当 dict key / set 元素。
本项目靠这个把「同一篇文档在两路召回里是同一个东西」变成可判定的事实。

## 2.4 async / await（必问）

**核心**：单线程事件循环 + 协程。`await` 的作用是**让出控制权**，不是开线程。

```python
async def handler():
    a = await llm_call()      # 等网络，期间可以跑别的请求
    b = await db_query()      # 同上
```

**和线程的区别**：

| | 线程 | 协程 |
|---|---|---|
| 切换 | 操作系统，微秒级 | 用户态，纳秒级 |
| 数量 | 几百到几千 | 几万到几十万 |
| 竞态 | 处处要锁 | 只在 await 点可能切换 |
| 适合 | CPU 密集 / 阻塞调用 | IO 密集 |

**最容易踩的坑**：**在协程里调用同步阻塞函数会卡死整个事件循环**。
> 一个 `requests.get()` 或者 `time.sleep()` 写在 async 函数里，会让这个事件循环上所有并发请求一起卡住。要么用 `httpx.AsyncClient`，要么用 `asyncio.to_thread()` 丢到线程池。

## 2.5 ContextVar（本项目用它传 request_id）★

**为什么不用 `threading.local`**：
> `threading.local` 假设「一个线程只服务一个请求」—— 这在 async 服务里是**错的**。一个事件循环线程上会并发跑成百上千个协程，thread-local 会让同线程的请求读到彼此的 request_id。

**ContextVar 怎么工作**：`asyncio` 创建 Task 时会**复制当前上下文**，所以 `create_task` 起的子任务、`await` 链上的任何一层都能读到同一个值。

**诚实的代价**：
> `ContextVar` 不会自动跨线程。`asyncio.to_thread()` 里读不到调用方的 request_id。真要带过去就用 `contextvars.copy_context().run(...)`。

# 第 3 章 FastAPI

## 3.1 为什么选它

- 原生 async（Agent 全是 IO 等待，同步框架会浪费掉）
- Pydantic 自动做请求/响应校验 + 自动生成 OpenAPI
- 依赖注入比 Flask 的装饰器清晰

## 3.2 依赖注入（Depends）

```python
async def current_user(token: str = Depends(oauth2_scheme)) -> User:
    ...

@app.get("/api/reservations")
async def list_mine(user: User = Depends(current_user)): ...
```

**关键**：`Depends` 的返回值是**自动注入**的 —— 身份来自认证链路，**不来自请求体**。
这条在项目里是硬规矩（见第 11 章）。

## 3.3 lifespan（启动/关闭）

```python
@asynccontextmanager
async def lifespan(app: FastAPI):
    await init_state_db()      # 启动：建连接、准备状态库
    yield
    await close_pool()         # 关闭：释放连接
```

**比 `@app.on_event` 好**：一个函数管住一对，顺序清晰，异常也能正确传播。

## 3.4 中间件与异常处理

**中间件管「所有请求都要做的事」**：request_id 注入、耗时统计、访问日志。
**异常处理器管「把内部异常翻译成 HTTP 语义」**：`LLMError` → 502，`ValidationError` → 422。

**注意**：不要在中间件里做业务判断 —— 它拿不到依赖注入的对象，而且抛异常的位置会很尴尬。

## 3.5 SSE（Server-Sent Events）★

本项目用 SSE 做流式回复：

```python
return StreamingResponse(_gen(), media_type="text/event-stream", ...)
```

**SSE 长什么样**：

```
data: {"delta": "明天"}

data: {"delta": "下午"}

data: {"done": true}

```

**格式规矩**：每个事件以 `data:` 开头，**两个换行 `\n\n` 结尾**。少一个换行浏览器就不触发。

**和 WebSocket 的取舍（必问）**：

| | SSE | WebSocket |
|---|---|---|
| 方向 | 单向（服务端→客户端） | 双向 |
| 协议 | 就是 HTTP | 独立协议 |
| 自动重连 | 浏览器内置 | 要自己写 |
| 经过代理/网关 | 友好（就是 HTTP） | 有些网关要额外配置 |

**项目里的一个具体决定（面试可以讲）**：
> 我没有用浏览器的 `EventSource`，而是用 `POST + fetch` 手工读流。因为 `EventSource` 只支持 GET，把用户那句话塞进查询串既受长度限制（中文还要编码），也会把用户输入写进访问日志。

**这个细节很能说明你懂**：知道规范，也懂为什么不能照抄规范。

# 第 4 章 Pydantic v2

## 4.1 三件作用

1. **请求/响应校验**（FastAPI 自动用）
2. **配置管理**（`BaseSettings` + 环境变量前缀 `LAB_`）
3. **给模型生成 tool schema**（本项目这么用）

## 4.2 一个模型，两处生效 ★

```python
class CreateReservationParams(BaseModel):
    model_config = ConfigDict(extra="forbid")
    equipment_id: int = Field(description="设备 ID，来自可用性查询结果")
    date: dt.date = Field(description="预约日期 YYYY-MM-DD")
```

**面试可以这么讲**：
> 我用 pydantic 模型而不是手写 schema 字典：同一个模型既用于**生成**给模型的 JSON Schema（`model_json_schema()`），也用于**校验**模型回传的参数。一处定义两处生效，就不会出现「改了字段忘了改 schema」那种漂移。

## 4.3 `extra="forbid"` 为什么重要

> 模型多给一个字段应当被**明确拒绝并回喂**，而不是静默忽略 —— 静默忽略会让它以为参数生效了，下一轮继续错。

**这句话揭示了 Agent 工程的一个原则**：错误要「响」，要能进入下一轮的重试循环。

## 4.4 ValidationError 的用法

```python
try:
    params = spec.params.model_validate(raw)
except ValidationError as exc:
    return ToolResult(ok=False, error=exc.errors())   # 失败也是一条数据
```

**注意这里没抛异常** —— 见第 5.4 节「失败也是一条数据」。

# 第 5 章 大模型基础（面经高频）

## 5.1 几个必须分清的参数

| 参数 | 作用 | 无常 / 高值的后果 |
|---|---|---|
| **temperature** | 采样随机性，0 = 几乎确定 | 高 → 输出飘、JSON 更容易坏 |
| **top_p** | 核采样，只从累积概率前 p 里抽 | 和 temperature 别同时调 |
| **max_tokens** | 输出长度上限 | 太小 → JSON 被截断，解析炸 |
| **context window** | 输入+输出总预算 | 超了直接报错或被静默截断 |

**做结构化抽取时**：temperature 设 0 或很低，加 `response_format=json_object`。

## 5.2 Function Calling（Tool Calling）怎么工作 ★★★

```
① 你把工具的 JSON Schema 交给模型（tools=[...]）
② 模型不直接执行，它回一个 tool_calls：{name, arguments}
③ 你的代码执行工具，把结果作为 role=tool 的消息塞回去
④ 模型看到结果，继续推理或给出最终回答
```

**最关键的一句**：
> **模型不执行任何东西，它只是输出一个「我想调这个工具、参数是这些」的结构化意图。** 真正执行的是你的代码。

**这解释了两件事**：
1. 为什么可以「有副作用的工具默认不给模型看」—— 因为给了它就能请求执行
2. 为什么工具内部必须自己校验参数 —— 模型给的参数是**不可信输入**

## 5.3 JSON 模式的坑：模型会裹代码围栏 ★

代码里的真实记录：
> Moonshot 的 kimi-k2.6 即使带了 `response_format=json_object`，也会把输出包成 ```` ```json\n{...}\n``` ````。参数保证了围栏**里面**是合法 JSON，但围栏本身让 `json.loads` 在第 0 个字符就炸。

**处理顺序**：先剥围栏，剥完直接解析。
**刻意没做的事**：更花哨的「提取首个 JSON 对象」先不做 —— 等真出现围栏之外的花样再加，**不为想象中的模型行为写代码**。

**面试可以说**：这句话体现的是「按实测写代码，不按想象写代码」。

## 5.4 失败也是一条数据（一个很好的设计观点）★

`ToolResult` 的设计决定：

```python
@dataclass
class ToolResult:
    name: str
    ok: bool
    payload: Any = None
    error: str = ""
    truncated: bool = False
    elapsed_ms: float = 0.0
```

**代码注释原话**：
> 模型给错参数是最常见的失败形态，而那种情况需要把「错在哪」回喂给它重试。若这里抛异常，重试循环就得在调用点再包一层 try —— 不如一次性建模成数据，让成功与失败在类型上是同一件事，调用方只有一条路径要写。

**为什么这是好设计**：Agent 的本质是**循环**（调工具 → 看结果 → 再调）。
如果失败是异常，这个循环里就有两条控制流；如果失败是数据，就只有一条。

## 5.5 上下文预算与结果截断 ★★

**问题**：一次检索返回几万字，直接塞回上下文会把预算吃光。

```python
DEFAULT_RESULT_LIMIT = 1200   # 单次工具结果回喂的字符上限
```

**取值理由（注释原话）**：
> 一次检索/协商的结构化结果通常在 1–3 KB；超过这个量级的多半是「把整个库倒出来」而不是「回答问题」。

**★ 截断的一个必须注意的点**：
> 截断时保留头部并留一个**明确的截断标记** —— 模型必须知道自己看到的是节选，否则它会基于残缺内容接着编。

**面试怎么讲**：
> 工具结果我做了截断，上限 1200 字符。但关键不是截断，是**告诉模型被截断了** —— 不告诉它，它会拿半截数据当完整数据推理，那比不给更糟。同时 `payload` 保留未截断的完整对象给响应层用，模型看截断版。

**这个问题面经直接问过**（「上下文管理」那一题），答这个就很稳。

## 5.6 重试与超时

- **超时**：模型调用必须设，否则一个卡住的请求会把并发槽占死
- **重试**：只重试**可重试**的错误（超时、429、5xx），不重试 400（参数错，重试也没用）
- **退避**：指数退避 + 抖动，避免重试风暴
- **熔断**：连续失败到阈值就直接快速失败，别让每个请求都等满超时

**项目里的原则**：模型调用失败 → 走降级，**不把异常抛给用户**。

# 第 6 章 Agent 与 LangGraph（最重要的一章）

## 6.1 Agent 到底是什么

**一句话**：Agent = 大模型 + 工具 + 一个循环。

```
while 还没完成 and 步数没用完:
    模型决定下一步（调哪个工具 / 给最终回答）
    代码执行工具
    把结果塞回上下文
```

**和普通 LLM 应用的区别**：普通应用是「一次输入 → 一次输出」；Agent 是「多次模型调用 + 多次工具调用」的循环。

**这就带来三个工程问题**（面试常追问）：
1. **什么时候停**：步数上限、模型给最终回答、检测到循环
2. **工具怎么选**：模型选（ReAct）还是代码选（图路由）
3. **失败了怎么办**：重试、降级、把错误回喂

## 6.2 ReAct 模式

**Re**asoning + **Act**ing：模型交替进行「思考」和「行动」。

```
Thought: 用户想要明天下午的光谱仪，我需要先查可用性
Action: query_availability(date=2026-10-21, ...)
Observation: 14:00-16:00 空闲
Thought: 有空，但还要确认资质
Action: check_admission(query=光谱仪需要什么资质)
Observation: 需要培训证书
Thought: 用户没有资质，应该告知并提出替代方案
Final Answer: ...
```

**优点**：灵活，能处理没预料到的路径。
**缺点**：不确定性高 —— 模型可能选错工具、反复调同一个、或者不按格式回复到步数用尽。

**这就是本项目默认不走 ReAct 的原因**（见 1.4 节）。

## 6.3 LangGraph 核心概念 ★★★★★

**LangGraph = 把 Agent 写成一张状态图。**

| 概念 | 说明 |
|---|---|
| **StateGraph** | 图，状态是一个 TypedDict |
| **节点 node** | 一个函数：读 state，返回要更新的字段 |
| **边 edge** | 固定流转 A → B |
| **条件边 conditional_edge** | 根据函数返回值决定去哪 |
| **END** | 终止 |
| **checkpointer** | 持久化状态（本项目没用 PG checkpointer，见 6.7） |

**本项目七节点**（`src/lagent/agent/graph.py:133-139`）：

```python
graph = StateGraph(AgentState)
graph.add_node("parse", self._parse)          # 理解语言 → 结构化诉求
graph.add_node("ask", self._ask)              # 信息不全时追问
graph.add_node("negotiate", self._negotiate)  # 查空闲 + 校验资质 + 算备选
graph.add_node("book", self._book)            # 真的下单
graph.add_node("cancel", self._cancel)        # 取消
graph.add_node("retrieve", self._retrieve)    # 检索规范文档
graph.add_node("compose", self._compose)      # 措辞成自然语言
```

**干的边**：

```python
graph.set_entry_point("parse")
graph.add_conditional_edges("parse", self._after_parse, {
    "cancel": "cancel",
    "retrieve": "retrieve",
    "negotiate": "negotiate",
    "compose": "compose",
})
graph.add_conditional_edges("ask", self._after_ask, {"ask": END, "negotiate": "negotiate"})
graph.add_edge("negotiate", "book")
graph.add_edge("book", "compose")
graph.add_edge("cancel", "compose")
graph.add_edge("retrieve", "compose")
graph.add_edge("compose", END)
```

**★ 面试必被追问：为什么「negotiate → book」是固定边，不是条件边？**

因为 `negotiate` 内部已经决定了 `satisfied` 是 true 还是 false，
`book` 节点自己会检查 `satisfied`，不满足就什么都不写直接过。
**这个设计的好处**：图的结构保持简单（少一个决策点），判定逻辑留在业务节点里。

**如果答成「因为条件是 negotiate 算出来的所以直接连」—— 不够**。要说出「book 内部自检」这层。

## 6.4 LangGraph vs LangChain ★★★★

| | LangChain | LangGraph |
|---|---|---|
| 抽象 | 链（Chain），线性为主 | 图（Graph），支持环和分支 |
| 控制流 | 顺序 + 少量路由 | 任意有向图 + 条件边 |
| 状态 | 靠链的中间变量 | 显式 state，可持久化 |
| 适合 | 简单流水线（检索→生成） | 多步 Agent、需要回退/重试/人工介入 |
| 调试 | 链长了难看清 | 图可可视化，每步 state 可查 |

**面试答法**：
> LangChain 解决的是「把组件拼起来」，LangGraph 解决的是「控制流本身是复杂的」。Agent 有环（调工具后回到模型）、有分支（不同意图走不同路径）、要能中断和恢复，这些用链表达很别扭。LangGraph 就是把状态机显式写出来，代价是你要自己设计 state 和边界。

**加分点**：
> 而且 LangGraph 不是必须的 —— 如果流程是线性的，自己写 if/else 更清楚。我选它是因为这个项目有七条分支和跨轮状态。

## 6.5 工具设计：Tool vs Skill（面经原题）★★★

**这道题面经里出现过，很多人答不清**。

| | Tool（工具） | Skill（技能） |
|---|---|---|
| 是什么 | 一个**函数**，有明确参数 schema | 一段**可复用的知识与流程**（通常是 markdown 指令 + 可能的脚本）
| 谁执行 | 代码执行 | 模型读了之后**按里面的步骤自己去做** |
| 作用 | 提供**能力**（查库、下单） | 提供**方法**（怎么做这件事） |
| 例子 | `query_availability(date)` | 「如何写一份合规的预约说明」的步骤文档 |
| 确定性 | 高（代码说了算） | 低（模型理解后执行） |

**一句话区分**：
> Tool 是「给你一只手」，Skill 是「教你一套做法」。

**什么时候用哪个**：
> 需要**执行**、需要**副作用可控**、需要**参数校验**的事，做成 Tool。需要**领域知识**、**多步流程**、**写作规范**的事，做成 Skill。

**和本项目的关系**：
> 我的项目里工具是 Tool（`query_availability` / `create_reservation`），而「怎么判断该不该追问」「规范文档怎么检索」更接近 Skill —— 前者的判定逻辑我写进了代码（确定性优先），后者我做成知识检索。

## 6.6 多 Agent 协作（面经原题）★★★★

**先说结论**：**本项目没做多 Agent，因为不需要。**

**但要能讲清楚什么时候需要、怎么传信息**：

**三种协作形态**：

| 形态 | 说明 | 适合 |
|---|---|---|
| **Supervisor**（主管） | 一个 agent 分派任务给几个专家 agent | 任务可以明确切分 |
| **Pipeline**（流水线） | A 的输出是 B 的输入 | 阶段清晰（抽取 → 检索 → 生成） |
| **Debate / 反思** | 多个 agent 互相审 | 需要提高准确率、有验证手段 |

**信息怎么传**：

1. **共享 state**（LangGraph 的典型做法）：所有 agent 读同一个 state，字段是契约
2. **消息传递**：agent 间发消息，各自有上下文
3. **文件/数据库**：落盘交换（最重，但可审计）

**★ 最关键的一句（能救场）**：
> 多 Agent 的主要成本不是 token，是**上下文不一致**。两个 agent 各自维护一部分状态，一旦对「当前诉求是什么」理解不同，错误会被放大而不是被平均掉。所以我倾向于：**能用一张图 + 一个共享 state 解决的，就不要拆成多个 agent。**

**为什么这是加分回答**：面经问「多 agent 怎么协作」，很多人背完 supervisor 就完了。你补一句「什么时候不该用」，立刻区分开。

## 6.7 会话状态存储（一个真实取舍）★

`state.py` 里有两种后端：

- `SessionStore` —— 进程内 dict，默认。单进程最简单
- `SqliteSessionStore` —— 同机多进程共享（WAL），重启不丢

**注释原话（诚实边界）**：
> 两者都不是分布式方案：跨**机器**的多副本仍需要 Redis / 共享数据库（PG 下更该用 LangGraph checkpointer）。本项目不假装一个 SQLite 就解决了分布式 —— 但「多进程」这个真实需求已经被接住了。

**面试怎么讲**：
> 会话状态我做了两级：默认进程内，需要多进程就切 SQLite（WAL 模式）。但我明确不声称它能跨机器 —— 那需要 Redis 或者 LangGraph 的 PG checkpointer。我把「多进程」这个真实需求接住了，把「分布式」留给下一阶段。

## 7.1 切片（Chunking）★★★★

**这是面经第一题，也是最容易答得空的一题。**

### 四种策略

| 策略 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| 固定长度 | 每 N 字符切 | 简单 | 切断语义 |
| 固定长度 + 重叠 | 每 N 切，重叠 M | 缓解切断 | 索引变大 |
| **按结构切** | 按标题/段落切 | **语义完整** | 依赖文档有结构 |
| 语义切 | 按向量相似度找边界 | 最贴合语义 | 慢、贵 |

### 本项目的做法（有明确理由）★

```python
def load_corpus(path):
    """按 ``## `` 标题切块。规范文档天然以小节为单位，不需要滑窗。"""
```

**为什么按标题切而不滑窗**：
> 这是规范文档，每一条规则天然是一个小节，整条切下来语义完整。滑窗反而会把一条规则从中间劈开 —— 上半句说「需要资质」，下半句说「例外情况」，切开了两个都不完整。

**★ 但比「策略名」更值钱的是它的实现细节**：
> 每个块都带 source（文档名）+ heading（小节标题），答案能指回「《实验室安全规范》· 离心机使用」这一节。

**为什么用标题定位，而不是行号**：
1. **可追溯**：模型说「离心机需要培训证书」，人可以直接翻到那一节核对 —— 行号在文档一改版就全错
2. **可审计**：出问题时按 heading 定位是哪一条规则导致的答案
3. **便于更新**：块指纹 sha1(source + heading + text) 变了就知道哪一块改过

**诚实的边界（这里别硬吹「标行号」）**：
> 这个项目**没有实现行号**。Chunk 只有 source / heading / text 三个字段（retriever.py:46-49）；load_corpus 用 read_text().splitlines() 之后按 ## 分块，行号在拆分时就丢了。规范文档天然的定位单位是「哪一节」而不是「第几行」，所以标题够用。**如果被追问「能不能点回原文第几行」，答案是「不能，只能到节」** —— 别顺着面试官说能。

**面试怎么答（完整版）**：
> 切片要看文档形态。通用文档用固定长度加重叠，因为不知道边界在哪。我的场景是安全规范，天然按小节组织，所以按标题切 —— 语义完整，而且能保留「这是哪一条规则」这个信息。每个块还带着小节标题，因为回答需要可追溯：模型说「离心机需要培训证书」，我要能指回《安全规范》的哪一节。**切片策略不是选最优的，是选和文档结构匹配的。**

**这句话是这题的满分点**：切片策略不是选最优的，是选和文档结构匹配的。

## 7.2 词元化：中文的特殊问题 ★★

**问题**：中文没有空格，BM25 这类基于词频的算法需要「词」。

**三种做法**：

| 做法 | 说明 | 代价 |
|---|---|---|
| 单字切 | 「离心机」→ 离/心/机 | 太碎，噪声大 |
| **字符二元组** | 「离心机」→ 离心/心机 | 便宜，效果好 |
| 分词库（jieba） | 离心机 | 引入依赖 + 词典维护 |

**本项目的选择**：

```python
# 中文没有空格分词，用字符二元组做词元；英文与数字按词切。
# 二元组对中文短查询的召回明显好于单字，成本又远低于引入分词库。
_ASCII = re.compile(r"[a-z0-9]+")
_CJK = re.compile(r"[\u4e00-\u9fff]+")
```

**面试怎么讲**：
> 中文要先解决分词。我选了字符二元组：单字切太碎噪声大，jieba 要引入依赖还要维护词典。二元组对短查询的召回明显更好，成本又低得多。这是一个典型的「够用就好」的取舍。

## 7.3 BM25 算法（手写了，没引库）★★★

**公式**：

```
score(D, Q) = Σ idf(qi) * [ tf(qi,D) * (k1+1) ] / [ tf(qi,D) + k1*(1 - b + b*|D|/avgdl) ]
```

**两个参数**：

| 参数 | 默认 | 作用 |
|---|---|---|
| **k1** | 1.5 | 控制**词频饱和**。tf 再高，得分也有上限 |
| **b** | 0.75 | 控制**长度归一化**。b=1 完全按长度罚，b=0 不罚 |

**为什么要 k1（词频饱和）**：
> 一个词出现 100 次不代表相关度是出现 1 次的 100 倍。k1 让高频词的收益递减。

**为什么要 b（长度归一化）**：
> 长文档天然更容易包含查询词，不归一化的话长文档永远排前面。b 就是惩罚长度。

**IDF**：

```python
idf = math.log(1 + (n - freq + 0.5) / (freq + 0.5))
```

**含义**：越少见的词权重越高。「的」这种词 idf 接近 0。

**面试如果问「BM25 和 TF-IDF 的区别」**：
> TF-IDF 的词频是线性的，BM25 加了一个饱和函数（k1），并且显式做长度归一化（b）。所以 BM25 不会因为某文档里关键词重复很多次就把它顶到第一。

## 7.4 向量检索与 Embedding ★★★★

**Embedding 是什么**：把文本映射成一个高维向量，语义相近的文本向量距离近。

```
"离心机需要什么资质"  → [0.12, -0.83, 0.44, ...]  (1024 维)
"离心机的准入要求"    → [0.11, -0.81, 0.46, ...]  ← 很近
"荧光光谱仪怎么用"    → [0.67,  0.21, -0.05, ...] ← 远
```

**相似度算法**：

| 算法 | 公式 | 说明 |
|---|---|---|
| 余弦相似度 | cos(A,B) = A·B / (\|A\|\|B\|) | 最常用，只看方向不看长度 |
| 点积 | A·B | 向量已归一化时等价于余弦 |
| 欧氏距离 | \|A-B\| | 越小越近 |

**本项目把距离转成相似度**：

```python
out.append((chunk, 1.0 / (1.0 + float(dist))))   # 距离 → 相似度，单调递减
```

### bge-m3（面经原题）★★★

**如果被问「你们用什么 embedding 模型」并提到 bge-m3，要能说清它是什么**：

| 特性 | 说明 |
|---|---|
| **多语言** | 中英等 100+ 语言，M3 = Multi-lingual |
| **多粒度** | M3 = Multi-granularity，支持长文本（8192 token） |
| **多功能** | M3 = Multi-functionality：dense（稠密向量）+ sparse（稀疏，类似 BM25）+ multi-vector（ColBERT 式） |
| 来源 | BAAI（智源） |

**为什么「多功能」重要**：
> 一个模型能同时出稠密和稀疏向量，就不用再单独维护一套 BM25 索引，混合检索的两个分支可以来自同一个模型。

**诚实的说法**：
> 我项目里用的是 Chroma 自带的默认 embedding，规模很小（规范文档就几十个块），没有引 bge-m3。bge-m3 是生产规模下的选择 —— 它的价值在多语言和长文档，我这边两个都不需要。

**不要说「我们用了 bge-m3」如果不是真的** —— 一追问「它的三个 M 分别是什么」就露馅。

## 7.5 混合检索与 RRF ★★★★★

**为什么需要两路**：

| | BM25（稀疏/关键词） | 向量（稠密/语义） |
|---|---|---|
| 强项 | 精确词命中、专有名词、型号 | 同义改写、语义相近 |
| 弱项 | 换个说法就召不回 | 精确 ID、罕见词容易飘 |
| 例子 | 查「XRD-7000」 → 稳 | 查「拍片子要什么手续」→ 稳（理解成 X 光） |

**结论**：两路互补，所以要做混合。

### RRF（Reciprocal Rank Fusion）★★★

**公式**：

```
score(doc) = Σ_over_paths  1 / (k + rank(doc))

k 通常取 60
```

**★ 为什么用 RRF 而不是加权求和分数**：
> 因为 BM25 的分数是**无界的**（可以到几十），余弦相似度是 **0–1** 的。量纲不可比，加权求和就必须先归一化，而归一化又要选方法（min-max？z-score？），每选一次就多一个拍脑袋的参数。**RRF 只吃排名，不吃分数**，天然规避了这个问题。

**★ 为什么 k=60**：
> k 控制「排名靠前的优势有多大」。k 越小，rank0 和 rank1 的分差越大，越偏向单路的最优结果；k 越大，各路越平均。60 是原论文（Cormack et al. 2009）的经验值，实践中 10–100 都常见。

**面试如果被追问「k 怎么选」**：
> 我沿用了论文的 60。它的作用是平滑：k=0 时 rank0 得 1 分、rank1 得 0.5 分，差距很大；k=60 时是 1/61 和 1/62，几乎一样。所以 k 大 = 更相信「多路都提到」而不是「某一路排第一」。这个项目里召回池很小，60 足够。

### 本项目 RRF 的两个实现细节 ★★★

**① 合并键必须用内容指纹，不能用 chunk.id**

**代码 docstring 里记的真实教训**：
> 上个项目的 RRF 融合用 `chunk.id` 做两路结果的合并键，而 BM25 那一路的 id 是 `source#N`、向量那一路是 `instance_id#N` —— 两边永远不相等，于是「两路互相印证」这个机制**从头到尾没有生效过**，同一篇文档还会在结果里出现两次。当时测试全绿，因为那个断言只检查了「分数高于某阈值」，而单路 rank0 的分数恰好也能过。

**修法**：

```python
@property
def fingerprint(self) -> str:
    raw = f"{self.source}\x00{self.heading}\x00{self.text}"
    return hashlib.sha1(raw.encode("utf-8")).hexdigest()
```

**并且补了两条断言**：
1. 融合结果里**不存在重复正文**
2. 两路都命中的文档分数**严格高于**单路 rank0 的 `1/(k+1)`

**这段是整份文档最值钱的面试素材之一。** 讲法：
> 我的 RRF 融合用内容指纹做合并键，不用 chunk.id。因为在上一个项目里，两路的 id 格式不一样（一路是 `source#N`，一路是 `instance_id#N`），永远对不上，导致「两路印证」这个机制从来没生效过，同一篇文档还会重复出现。而测试是绿的 —— 因为断言只检查分数阈值，单路 rank0 恰好也能过。所以这次我加了「结果里不能有重复正文」和「两路都命中必须严格高于单路最高分」两条断言，让这个 bug 藏不住。

**为什么会打动面试官**：它同时展示了三件事 —— 你踩过坑、你知道测试为什么会漏、你把教训变成了断言。

**② 可观测：记录每条命中由哪几路支撑**

```python
self.last_matched: dict[str, list[str]] = {}
# 注释：单路命中的可信度低于两路命中，这个字段让「两路印证」变成可断言的事实，而不是一句宣传语。
```

**这个字段最后会出现在返回的 DocHit.matched_by 里**，前端能看到「这条是怎么被找到的」。

## 7.6 重排（Re-ranking）与 Cross-Encoder ★★★★

**面经原题，必须能说清 Bi-Encoder 和 Cross-Encoder 的区别**。

| | Bi-Encoder（双塔） | Cross-Encoder（交叉编码器） |
|---|---|---|
| 输入 | query 和 doc **分别**编码 | query 和 doc **拼在一起**编码 |
| 交互 | **没有**交互，最后算向量相似度 | 每个 token 对之间都做注意力 |
| 速度 | **快**（doc 向量可预计算） | **慢**（每个 query-doc 对都要跑一次） |
| 精度 | 较低 | **更高** |
| 用途 | **召回**（海量里粗筛） | **重排**（几十个里精排） |

**标准两阶段架构**：

```
100 万文档  --Bi-Encoder 召回-->  100 条  --Cross-Encoder 重排-->  5 条  → 给模型
   （快，能扛量）                    （慢，但只算 100 次）
```

**★ 为什么不能全用 Cross-Encoder**：
> 因为它的计算量和文档数量成正比，而且每来一个新 query 都要重算全部。100 万文档跑不动。所以只能用在召回之后的几十到几百条上。

**面试答法**：
> 重排用 Cross-Encoder，和召回用的 Bi-Encoder 是两种结构。Bi-Encoder 把 query 和 doc 分开编码，doc 向量可以离线算好，所以快，适合从海量里召回。但两边没有交互，精度有限。Cross-Encoder 把 query 和 doc 拼起来一次过模型，token 之间有完整注意力，精度高得多，但每个组合都要算一遍，贵。所以标准做法是两阶段：先召回 50–100 条，再重排取前 5。

**如果被问「你项目用了吗」—— 诚实答**：
> 没有。我的召回池只有几十个块，RRF 融合后的 Top-4 直接给模型就够用了，加一层 Cross-Encoder 只会让延迟翻倍而质量提升测不出来。**重排的收益和召回池大小成正比，池子小的时候不值得。**

**最后这句是加分点**：说明你不是背了个方案，你知道它的适用条件。

## 7.7 幻觉（Hallucination）★★★

**面经原题：怎么减少幻觉。**

### 幻觉的三种成因

| 类型 | 成因 | 例子 |
|---|---|---|
| **知识缺失** | 模型根本没有这个知识 | 编一个不存在的制度条款 |
| **检索没召回到** | RAG 找错了材料，模型硬答 | 问资质，召回了使用说明 |
| **指令遵循失败** | 模型忽略「只根据材料回答」 | 材料里没有，它自己补充 |

### 七种手段

1. **检索质量**：召回不到时**明确说不知道**，而不是硬答
2. **Prompt 约束**：明确写「只根据以下材料回答，材料没有就说没有」
3. **引用**：要求输出引用来源，人能核对（本项目返回 citations + matched_by）
4. **结构化输出**：JSON schema 约束，减少自由发挥
5. **temperature 调低**
6. **后置校验**：检查答案里的关键事实是否在材料中出现
7. **重排**：提高送进 prompt 的材料质量

### 本项目的特殊做法（最值钱的答法）★

**这个项目的关键判断是：业务事实不交给模型。**

> 预约能不能成，由规则代码算（时间段冲突、资质校验）。模型只负责两件事：把自然语言翻成结构化诉求、把结构化事实措辞成自然语言。它**没有机会**编造「明天下午有空」这种事实，因为那是代码算出来的。

**这就把幻觉从「系统性问题」降级成「表达问题」**：模型措辞可能不好，但它说的事实是真的。

**面试完整答法**：
> 幻觉我分两层处理。第一层是**不让模型掌握事实** —— 预约是否可用、有没有资质，这些由代码算，模型只做语言翻译和措辞，它编不出「有空」。第二层才是 RAG 那套：检索规范文档时给引用、prompt 里写死「材料没有就说没有」、召回不到时不硬答。我的判断是，**能用确定性代码解决的事不要交给概率模型**，这是最有效的抗幻觉手段。

## 7.8 意图识别与拒答（面经原题）★★★

**面经问到「意图审断」/「意图判别」**，本质是：怎么判断用户这个问题该不该答、该走哪条路。

**本项目的做法**：
> 意图分类是**独立的一次模型调用**（`classify_intent`），输出一个枚举，而不是让模型在自由文本里顺带决定。这样意图是**可测的** —— 评测集里可以逐条断言「这句话应该是 cancel 还是 create」，不需要解析自然语言。

**四种意图**（本项目）：create_reservation / cancel / ask_policy / smalltalk

**为什么要分类而不是一把梭**：
> 不同意图走**不同的图节点**。取消绝不该被路由到下单工具，规范问答不需要查空闲。分类把不确定性关在一个小盒子里。

**拒答这部分**：
> 项目里有安全边界 —— 每个工具内部自行校验参数与权限，不信任上游给的任何参数。有副作用的工具默认不暴露给模型。所以「模型想干坏事」在工具层就被拦了，不依赖意图识别挡。

## 7.9 RAG 评测（面经会顺带问）★★★

**要能说出测什么、怎么测**：

| 层 | 指标 | 怎么测 |
|---|---|---|
| **检索** | Recall@K、MRR、命中率 | 标注「这个问题该召回哪一块」 |
| **生成** | 忠实度（faithfulness） | 答案的事实是否都在材料里 |

# 第 8 章 PostgreSQL

## 8.1 和 MySQL 的主要区别

| | PostgreSQL | MySQL |
|---|---|---|
| 类型系统 | **强得多**（数组、范围、JSONB、自定义类型） | 相对简单 |
| 索引类型 | B-tree / Hash / GIN / GiST / BRIN | B-tree / Hash / 全文 |

| 复制 | 流复制、逻辑复制 | binlog 为主 |
| 序列 | SERIAL / IDENTITY | AUTO_INCREMENT |

**★ 一个能体现深度的问题：为什么 DDL 在事务里重要？**
> 迁移中途失败时，PG 能整体回滚，MySQL 会留下做了一半的表结构。这就是为什么 PG 上的迁移工具可以更放心。

## 8.2 JSONB（通用知识；本项目没用）

| | json | jsonb |
|---|---|---|
| 存储 | 原始文本 | **解析后的二进制** |
| 查询 | 要重新解析 | **可建索引** |
| 写入 | 快 | 稍慢（要解析） |

**JSONB 适合**：字段不固定、要查询但不需要强一致结构的场景。
**不适合**：核心业务字段 —— 能用列就用列，否则约束、索引、类型检查全丢了。

**★ 本项目的真实情况（别说错）**：
> 这个项目**一行 JSONB 都没有**（grep -rn JSONB src migrations 零命中）。它默认跑 SQLite，PG 只是 CI 里的一个 job。用的是 SQLAlchemy 的 sa.JSON()，三处：migrations/versions/0001_initial_schema.py:65 open_hours、:77 certs、:199 required_certs。

> **审计记录的 detail 也不是 JSON** —— src/lagent/models.py:525 是 detail: Mapped[str] = mapped_column(Text, default="")，就是一段文本。被追问「为什么审计明细不用 JSON」时，诚实答案是「当时不需要按字段查，文本够了；真要按字段查，就该拆列或上 JSONB，而不是继续塞字符串」。

# 第 10 章 可观测性（面经 22% 的工程题里高频）

## 10.1 结构化日志：为什么不是 print ★★★

代码里的三条理由（原话）：

1. **一行日志串不起一条链路**。一次 `/api/agent/chat` 会写审计、可能写门禁流水、可能触发下单。出问题时你想问的是「这一个请求到底发生了什么」，而自由文本里只有一堆互不相干的句子，没有任何共同字段能把它们挑出来。
2. **没有机器可读的字段**。「最近 5 分钟 5xx 有多少」这种问题，对着 print 的输出只能靠正则，而且每改一次日志文案就要改一次正则。
3. **没有耗时**。慢请求不会自己喊出来，你只知道「有时候慢」。

**所以做两件事**：日志变成**一行一个 JSON**，**每个请求有一个 request_id 贯穿全链路**。

## 10.2 request_id 的实现细节 ★★★

**用 ContextVar 而不是 threading.local** —— 见 2.5 节，这是 async 服务的正确做法。

**第二个细节：别用 logging.Filter 逐个 logger 挂**
> 常见写法是写一个 Filter 往 record 上补字段，然后挂到每个 logger 上。问题是「每个 logger」这个前提很难成立 —— 漏挂一个，那条链路就断了上下文，而且断得静默。这里改成**在 Formatter 里读上下文**：格式化发生在最后一步，只要日志最终经过这一个 handler，就一定有上下文。少一个需要维护的清单。

**第三个细节（这个很漂亮）：客户端给的 request_id 是不可信输入**

**攻击方式**：

```
X-Request-Id: abc
{"level":"ERROR","msg":"磁盘满了"}
```

**后果**：
> 原样写进日志，攻击者就能伪造出一条 ERROR；把 JSON 日志当数据源做告警的系统会直接被打穿。

**做法**：
> 入站值必须**白名单字符集 + 长度上限**，不合格就换一个新的，而不是「清洗一下接着用」—— **丢弃比修补更难被绕过**。

**面试怎么讲**：
> 我把日志做成了一行一个 JSON，每个请求一个 request_id 贯穿全链路。两个细节：一是用 ContextVar 而不是 thread-local，因为 async 里一个线程跑上千个协程；二是客户端传来的 X-Request-Id 是不信任的，它能用来做日志注入 —— 伪造一条 ERROR 日志打你们的告警系统。所以我用白名单字符集加长度上限，不合格直接丢弃换新的。

## 10.3 三层健康探针 ★★★

| 路径 | 作用 | 特点 |
|---|---|---|
| `/api/health` | **存活探针**（liveness） | **不碰数据库**，只证明进程能响应 |
| `/api/health/ready` | **就绪探针**（readiness） | 逐项报告依赖（DB、模型） |
| `/api/health/details` | 业务统计 | **需要登录** |

**为什么必须分开（k8s 场景下这个区别是致命的）**：
> 存活探针失败会**重启容器**。如果存活探针里查数据库，数据库抖一下就会导致所有健康实例被重启 —— 雪崩。就绪探针失败只是**摘流量**，不重启。

**为什么 details 要加认证**：
> 代码注释里写了原因：原来任何人不需要凭据就能看到业务统计（有多少积压）。这是信息泄露。

**★ 还有一个细节**：`ready` 里 `ok=False` 时**不说积压了多少**：
> 代码注释：「要数字去 `/api/health/details`（需要登录）」。所以哪怕 ok=False 也不说积压了多少。

## 10.4 指标

| 类型 | 用途 |
|---|---|
| Counter | 只增（请求数、LLM 重试数） |
| Gauge | 可增可减（当前积压） |
| Histogram | 分布（耗时 p50/p99） |

**本项目埋的点**：LLM 调用次数/耗时、重试次数、限流触发数、状态后端类型。

**为什么这些点**：它们全部对应一个**具体的不变量** —— 「模型调用应该成功」「重试不该频繁」「限流不该经常触发」。指标不是越多越好，是每个指标背后要有一个「不对了要看它」的场景。

# 第 11 章 安全

## 11.1 身份不来自请求体（项目硬规矩）★★

**代码里的原话**：「`user_id` 不出现在任何工具的参数 schema 里」—— 它由注册表从**认证结果**注入。

**为什么**：如果 `user_id` 是参数，模型可以把它填成别人的，或者攻击者改请求体就能冒充。

**面试可以说**：
> 这是一条很容易被忽略的边界 —— 大部分教程里的工具签名是 `create_reservation(user_id, ...)`，看起来没问题，但这个 user_id 一旦暴露给模型就等于把身份判断交给了它。我把它从 schema 里彻底删掉，由认证链路注入。

## 11.2 token_version：不存黑名单也能强制下线 ★★★

**问题**：JWT 是无状态的，签发了就有效到过期。用户改密码/被禁用后，旧 token 还能用。

**三种解法**：

| 解法 | 代价 |
|---|---|
| Redis 黑名单 | 每个请求查一次 Redis |
| 短过期 + refresh token | 复杂度上升 |
| **token_version** | **零额外查询**（本来就查了 user 表） |

**本项目的做法**：

```python
if user is None or user.token_version != principal.token_version:
    # 拒绝

user.token_version = (user.token_version or 0) + 1   # 自增 = 所有在途令牌失效
```

**代码注释原话**：
> 有了 token_version 之后这条几乎是白送的 —— 自增世代即让所有在途令牌失效。

**面试怎么讲**：
> JWT 无状态，签发了就管不住。我用 token_version 而不是 Redis 黑名单：每个请求本来就要查用户表，比对一下版本号是零成本；要强制下线就把版本号加一，所有在途令牌立刻失效。黑名单方案每个请求都要多查一次 Redis，而且要考虑黑名单本身的过期清理。

**这正是面经里「JWT 为什么用 Redis」那道题的另一种答法** —— 你可以说「我的项目里没走 Redis 黑名单，走的是版本号」，然后讲清取舍。

## 11.3 限流：滑动窗口

```python
SlidingWindowLimiter(settings.rate_limit_per_minute, 60.0)
```

**三种限流算法**：

| 算法 | 问题 |
|---|---|
| 固定窗口 | 窗口边界处能过 2 倍流量 |
| **滑动窗口** | 精确，但要记录时间戳（本项目用这个） |
| 令牌桶 | 允许一定突发，最平滑 |

# 第 12 章 幂等与并发

## 12.1 幂等键（idempotency_key）★★★

**问题**：用户点了两次「确认预约」，产生两条记录。

**做法**：

```
客户端生成一个 uuid（同一次操作复用同一个）
  ↓
服务端查幂等表：
  有记录 → 直接回放上次的结果（不再执行）
  没记录 → 执行 + 记录结果（唯一索引防并发）
```

**★ 关键细节（面试会追问）**：

1. **幂等键由客户端生成**，不是服务端 —— 因为服务端不知道「这两个请求是同一次操作」
2. **要存结果而不只是存 key** —— 否则重复请求还是得重跑一遍，而且第二次可能结果不同
3. **并发下靠唯一索引**：两个请求同时查都没有 → 同时插入 → 一个成功一个撞唯一索引 → 撞的那个去读已存结果
4. **要设过期** —— 幂等表不能无限增长

## 12.2 三层并发防线

| 层 | 手段 | 防什么 |
|---|---|---|
| 请求层 | 幂等键 | 同一个操作重复提交 |
| 数据层 | **唯一索引** | 并发插入同一资源 |
| 行级 | **乐观锁**（version 字段） | 并发更新互相覆盖 |

**为什么不用分布式锁（和 Java 项目同一个判断）**：
> 锁只能锁单机；而且锁需要释放、需要考虑持有者崩溃。数据库的唯一约束和条件更新是**天然正确**的 —— 它不依赖任何一方活着。

## 12.3 乐观锁 vs 悲观锁

| | 乐观锁 | 悲观锁 |
|---|---|---|
| 做法 | 更新时校验 version | SELECT ... FOR UPDATE |
| 冲突时 | 更新失败，重试或报错 | **阻塞等待** |
| 适合 | 冲突少 | 冲突多 |
| 死锁 | 不会 | 可能 |

**本项目用乐观锁的理由**：预约冲突是**低频**事件（同一设备同一时刻很少被两个人同时抢），阻塞等待不划算。

# 第 13 章 测试与评测（面经 4 题，很能体现水平）

## 13.1 三档分开计分 ★★★★

**这是本项目最值得讲的方法论。**

```python
intent   意图识别命中期望意图
slots    槽位抽取的关键字段正确（日期 / 时间窗 / 设备）
e2e      端到端：最终给出期望形态的结果
```

**代码注释原话**：
> 为什么不合成：把三者混起来会掩盖退化。假设意图全对、槽位全错，合成分看着还有个七八成，实际系统已经不可用了。分开报才能一眼看出坏在哪一层。

**面试怎么讲**：
> 评测我分三档算，不合总分。意图、槽位、端到端分开。因为合起来会掩盖退化 —— 意图全对槽位全错，总分看着还有七八成，但系统已经废了。分开报才能看出坏在哪一层：是模型听不懂话，还是听懂了没抽对字段，还是抽对了但业务没走通。

**★ 这句「合成分会掩盖退化」是这类题的核心论点。**

## 13.2 固定评测集

```
eval/cases.yaml   —— 每个 case 有 message + 期望 intent + 期望槽位 + 期望 outcome
```

**七种 outcome**：

| outcome | 含义 |
|---|---|
| proposals | 给出备选方案 |
| available | 可直接约 |
| booked | 下单成功 |
| ask | 追问缺的信息 |
| blocked | 明确拒绝（无资质/冲突） |
| answer | 回答规范问题 |
| smalltalk | 闲聊 |

**为什么要固定集**：
> 改 prompt、换模型、调阈值，同一套 case 跑出来才能比较。没有固定集就没法回答「这次改动到底变好了还是变坏了」。

## 13.3 Mock LLM：一个很实用的设计 ★★★

**代码注释原话（三条理由）**：
1. 没网、没 key 也能跑通全流程与评测；
2. 评测的基线稳定 —— 换真实模型时差异只来自模型本身；
3. 把「中文时间表达怎么落地」这件苦活固定在可测的地方。

**关键设计**：Mock 实现的是**语义化方法**（`classify_intent` / `extract_requirement`），不是裸的 `chat()`。

> 这样 Mock 不必去猜系统提示词里想让它干什么，测试也不依赖提示词措辞。

**面试怎么讲**：
> 我做了 Mock LLM。关键不是「能脱网跑」，而是它实现的是语义化接口而不是裸 chat —— 所以测试不会因为改了一句 prompt 就全红。换真模型时其余代码一行不改。这也是为什么我用 Protocol 而不是继承。

**这里能连起来讲 2.1 的 Protocol** —— 说明你的设计是自洽的。

## 13.4 测试理念（和 Java 那份同一个）★

**每个测试都要能证明它抓得住 bug。**

**本项目的具体例子**（第 7.5 节那个）：
> RRF 的两条断言不是因为「应该测一下」，而是因为上个项目的测试**绿着但功能没生效**。断言写在哪，取决于你认为哪种 bug 最不可接受。

## 13.5 AST 静态检查：用测试守住分层 ★★

**代码注释原话**：
> **本模块（以及整个 harness 包）不 import 任何业务模块。** 依赖方向是「业务实现 harness 定义的接口」，不是反过来。这条边界由 `tests/test_harness.py` 里的 AST 静态检查钉住 —— 分层如果只写在文档里，迟早会被一次「顺手 import」破掉。

**这个做法很高级，面试可以直接讲**：
> 分层架构最容易破的方式是「顺手 import 一下」。我写了个测试，用 AST 解析 harness 包的源码，检查它没有 import 任何业务模块。这样 CI 会拦住这次顺手。

**为什么这比文档强**：文档是**愿望**，测试是**约束**。

# 第 14 章 项目中的六个核心设计（面试最值钱）

前面 13 章是通用知识，这一章是**只有做了这个项目才知道的**。

## 14.1 两种执行模式 + 三档降级 ★★★

```
react（模型选工具）
   ↓ 模型不听话 / 步数耗尽 / 格式错
deterministic（代码选工具）
   ↓ 模型显式关闭
引导式表单
```

**核心判断**：
> 模型负责理解语言，代码负责执行规则 —— 而「谁来选工具」是可配置的执行策略，不是世界观。

**诚实边界**：
> 这条链只覆盖「模型还在、只是不听话」。模型端点连不上它救不回来 —— 因为确定性路径也要模型做 NLU。那种情况是 502 + 前端切表单。

## 14.2 RRF 的合并键：一个被测试掩盖了两年的 bug ★★★

**上个项目的问题**：两路召回的 id 格式不同（`source#N` vs `instance_id#N`），用 id 做合并键永远对不上，导致：
- 「两路互相印证」这个机制**从来没生效过**
- 同一篇文档在结果里**出现两次**
- 而且**测试是绿的** —— 断言只检查分数阈值，单路 rank0 恰好也能过

**这次的修法**：
1. 合并键改成**内容指纹** `(source, heading, text)` 的 sha1
2. 加两条断言：结果里无重复正文；两路都命中必须严格高于单路最高分

**面试讲法**：
> 上一版项目的 RRF 有个 bug：两路召回用各自的 chunk id 做合并键，格式不一样永远对不上，所以「两路印证」从来没起作用，文档还会重复。但测试全绿 —— 因为断言只测了分数阈值。这次我把合并键改成内容指纹，并且加了两条断言让它藏不住：结果不能有重复正文，两路都命中必须严格高于单路最高分。**我从这次学到的是：测试绿不等于功能对，断言的形态决定了它能抓住什么 bug。**

## 14.3 有副作用的工具默认不给模型看 ★★★

```python
@dataclass(frozen=True)
class ToolSpec:
    side_effect: bool = False   # 有副作用 = 会写库或改变外部状态
```

**代码注释原话**：
> 让模型自由调用一个会写库的工具（下单、取消），等于把「误操作」降级成一次普通的工具调用 —— 模型没有后果意识，而这类错误对用户是真实损失。所以工具带 `side_effect` 标记，**默认不进入给模型的工具清单**。

**配套的另一条红线**：`user_id` 不出现在任何参数 schema 里，由认证结果注入。

**面试怎么讲**：
> 我的工具有副作用标记。会写库的工具默认不暴露给模型 —— 模型没有后果意识，让它自由下单等于把误操作降级成一次普通调用。有副作用的动作仍由业务代码显式调用，只是模型看不见、点不到。另外 user_id 从所有工具参数里删掉了，由认证注入 —— 身份不能来自模型。

## 14.4 失败也是一条数据 ★★

`ToolResult` 不抛异常，把失败建模成 `ok=False + error`。

**理由**：Agent 本质是循环，失败是循环里的正常一步（要把错误回喂给模型重试）。异常会让循环出现两条控制流。

**配套**：`extra="forbid"` 让模型多给的字段被**明确拒绝**，而不是静默忽略 —— 静默忽略会让它以为参数生效了，下一轮继续错。

## 14.5 上下文预算 + 截断必须告知模型 ★★★

```python
DEFAULT_RESULT_LIMIT = 1200

def for_model(self) -> str:
    if len(text) <= self.limit:
        return text
    return text[:self.limit] + f"\n…（结果已截断，原始 {len(text)} 字符）"
```

**关键不是截断，是告诉模型截断了**：
> 模型必须知道自己看到的是节选，否则它会基于残缺内容接着编。

**并且 `payload` 保留完整对象给代码用** —— 响应层要完整数据，模型只需要知道自己拿到了什么。

**这道题面经直接问过（上下文管理）**，这个答法很扎实。

## 14.6 三层健康探针 + 结构化日志 ★★

**三层**：liveness（不碰库）/ readiness（逐项依赖）/ details（业务统计，要登录）。

**为什么 liveness 绝不能碰库**：
> 存活探针失败会**重启容器**。数据库抖一下就重启所有健康实例 —— 雪崩。就绪探针失败只是摘流量。

**日志侧两个细节**：
1. `ContextVar` 而不是 thread-local（async 里一个线程跑上千协程）
2. 客户端传的 `X-Request-Id` 是**日志注入**通道，用白名单字符集 + 长度上限，不合格丢弃换新
