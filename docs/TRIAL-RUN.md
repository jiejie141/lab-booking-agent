## 3. 摩擦点

按严重度排。每条都带复现方式或证据，不写"感觉不太行"。

### 高

**H1 · 本轮补的管理功能，在控制台上一个都点不到**

控制台（`src/lagent/web/index.html`）一共只调 8 个接口：

```
/api/auth/login · /api/auth/me · /api/health/details · /api/labs
/api/reservations · /api/reservations/cancel · /api/users · /api/agent/chat
```

也就是说**审批、违约记录、通知、审计、门禁、备份**——这一轮补齐的六块——
管理员在界面上没有任何入口，只能 curl 或者读库。这与 P0-3 当初踩过的坑是同一类
（"后端有接口 ≠ 用户点得到"），那次我们给预约补了表单面板，但**管理侧没补**。

> 影响：一个实验室管理员实际上没法用这些功能。试运行期间"审批待办"和
> "违约记录"我都是调接口看的 —— 真实管理员不会这么做。

**H2 · 生产形态下备份功能整体不可用（已修）**

```
$ docker compose exec api python main.py backup
lagent.backup.BackupError: 找不到 pg_dump。…
$ docker exec api sh -c 'command -v pg_dump'   # 空
```

镜像里没装 PostgreSQL 客户端工具，而生产形态是 PG —— 所以备份在容器里**直接不可用**。
单元测试看不见：`tests/test_backup.py` 覆盖的是 SQLite 路径（`VACUUM INTO`），
PG 那条一直只有"代码看起来对"；只 `docker build` 也发现不了（Dockerfile 语法完全正确）。

**已修**：`Dockerfile` 装 `postgresql-client`。但**修完才发现真正的问题在下一条**。

**H3 · 装了也不够：客户端版本不对，dump 恢复不回来（已修）**

第一版修复装的是基础镜像自带的客户端 —— Debian 13 带的是 **17**，而服务端是 **16**。
备份"成功"了，恢复演练才炸：

```
psql:/drill/lab-….sql:13: ERROR: unrecognized configuration parameter "transaction_timeout"
```

pg_dump 17 会在 dump 头里写 `SET transaction_timeout = 0`，这个参数是 17 才有的 ——
**16 的服务端不认**。所以：

* 客户端比服务端**旧** → pg_dump 拒绝导出；
* 客户端比服务端**新** → dump 里带上服务端不认识的 GUC，**恢复到同一台库上直接失败**。

**结论：主版本必须与服务端一致。** 改成从 PGDG 装 `postgresql-client-16`，
并加 `ARG PG_MAJOR=16` 让"和 compose 里的 `postgres:16-alpine` 是一对"这件事显式可见。

> ★ 这条是整次试运行最有价值的发现：**"备份成功"与"能恢复"是两件事。**
> 如果只验备份文件非空，这个坑会一直躺到真出事那天 —— 而那正是最不能出事的时刻。
> 项目自己的原则写着"没演练过的备份不算备份"，这次是它救了一次。

**H4 · 备份与归档写在容器可写层，重建即丢（已修）**

`LAB_BACKUP_DIR=./var/backup`、`LAB_ARCHIVE_DIR=./var/archive` 都在容器内，
而 compose 只给 db 挂了卷，api 没有。`docker compose up --build` 一重建，
**备份和归档全没**。"备份被重建清掉"这件事只有在真需要恢复的那天才会被发现。

**已修**：compose 给 api 挂 `labvar:/app/var`，并注明取文件的方式
（`docker compose cp api:/app/var/backup ./var/`）。

**H5 · 预约不能改期，只能取消重约**

```
$ PATCH /api/reservations/9  {"start":"15:00","end":"16:00"}
HTTP 404        （没有这个路由）
```

想挪时间只能"取消 + 重新约"。危险在于**取消不可逆**（时段立刻释放），
而重约可能已经约不上 —— 一次"改个时间"的操作，可能让用户同时失去旧时段和新时段。
这是日常使用里最先被抱怨、也最容易补的缺口。

**H6 · 通知堆在库里没人管**

扫清扫日志：
```
✓ 通知投递   0 条   发出 0 条，失败 0 条，跳过 20 条（SMTP 未配置（LAB_SMTP_HOST 为空），通知只记录不投递）
```
* 20 条通知全部 `pending`；
* **没有任何东西提醒"SMTP 没配、通知在堆积"** —— 就绪探针里也没有这一项；
* 更麻烦的是**没有"全系统待发通知"的视图**：

| 调用 | 结果 |
|---|---|
| `GET /api/notifications`（管理员令牌，不带参数） | **0 条**（只看得到自己的） |
| `GET /api/notifications?user_id=2` | 18 条 |

也就是说管理员想确认"有没有卡住的通知"，必须**逐个用户去查**。

> 真实试运行里的表现：学生等不到审批结果邮件，会直接来问人 ——
> 而管理员手上没有能回答"到底发出去了没有"的页面。接口的 docstring 说
> "管理员能当场看到这条通知生成了没有"，但前提是他知道要指定哪个 user_id。

### 中

**M1 · 门禁不校验实验室开放时间**

只有**下单**路径校验 `open_hours`（`domain/availability.py`），
`domain/access.py` 里没有任何开放时间检查，全仓也没有 `lab_closed` 这类拒绝码。
实测：

```
现在 23:24（周六，分析楼 18:00 关门）
管理员签发一张 00:00–23:59 的凭证 → 刷卡 → granted=True · 已入场
```

正常流程下凭证窗口来自预约（⊆ 开放时间），所以问题只出在**手工签发**这条路径 ——
而手工签发正是"访客 / 临时人员 / 忘记预约的补救"用的，恰恰是最该谨慎的场景。
一个"进入前须更换专用鞋套"的细胞房在凌晨放人进去，是安全问题不是方便问题。

**M2 · 错误响应只有人话，没有机器可读的分类**

```
POST /api/reservations（撞车）→ 409  {"detail":"该时段刚被占用：2026-09-29 16:00-17:00"}
POST /api/reservations（无资质）→ 422  {"detail":"你缺少「离心」准入资质，…"}
```

进程内是有机器可读分类的（`BookingOutcome.reason` + `_BOOKING_STATUS` 映射），
但**过了 HTTP 边界就只剩 `detail`**。前端要区分"换个时段"和"去补资质"，
只能去解析中文文案 —— 而这正是项目自己在 `BookingOutcome` 的 docstring 里
明确反对的做法：*"抓『从人话里找关键词』当分类依据，是典型的「改一句文案，
指标就静默错位」"*。在进程内守住了这条原则，在 API 契约上漏了。

**M3 · CLI 在重建/恢复库之后打印 `Event loop is closed`**

```
$ docker exec api python main.py seed --force
…（正常输出）…
Exception closing connection <AdaptedConnection <asyncpg.connection.Connection …>>
RuntimeError: Event loop is closed
```

`restore` 与 `seed --force` 都能复现，**退出码仍是 0**。
数据侧没问题（恢复后逐表校验通过），但运维看到 traceback 会以为失败 ——
脚本里 `grep -i error` 也会误报。

**M4 · 闭馆时段基本做不了门禁演练**

接口层的时钟不可注入（`main.py` 里 `now_local()` 直接取真实时间），
只有领域函数和 `scripts/sweep_demo.py` 能传 `now=`。
所以晚上 23:24 想做门禁验收，只能看到 `permit_expired` ——
不是功能有问题，而是**没有任何办法把系统"假装调成下午两点"**。
培训新管理员、演示、验收都会撞上这个。

**M5 · 违约"只记不罚" + 没有面板 = 记录没人看**

`blocking_enabled=false` 是刻意的上线顺序（先观察判定准不准再处罚），这一点做对了。
但**配套缺失**：没有面板、没有摘要、没有告警。记录在案而没人看，
等于把"发现判定错误"的时间点推迟到真要处罚的那一天。

### 低

**L1 · 试运行产生的一次性数据没有清理入口。** 试运行时建的那台"需审批"设备，
只能直接改库删掉 —— 应用刻意没有删除路由（保历史，这个取舍是对的），
但也没有给管理员一个"归档 / 清理"的手段。

**L2 · 违约接口不给分解。** 返回的只有 `count`（计入的），豁免后直接归零。
管理员看不到"判过几次、其中几次被豁免"——想追责时这个区分很重要。

**L3 · 镜像里混进过本地运行产物（已由工作区改动修掉，但没提交）**

运行中的容器里有一个 `/app/var/ci_local.txt`，内容正是我本地跑的
"### pytest" 日志抬头。追下去发现：`.dockerignore` 在 HEAD 里**没有 `var/`**，
而工作区里有一份**未提交**的改动补上了它（还补了 `.github/`）。

所以时间线是：20:52 那次 `compose up --build` 用的是 HEAD 版本（不含 `var/`）→
本地产物被烤进镜像；22:53 那次重建（带上了工作区那份改动）就已经干净了
（实测新镜像的 `/app` 下没有 `var`）。

⚠️ **那份改动到现在还没提交** —— 也就是说仓库里"防止本地产物进镜像"这件事
目前**没有守门**，换台机器 clone 下来重新构建就会再犯一次。
本次一并提交（见 commit）。

**L4（环境，与代码无关）· Docker 守护进程写死了 `127.0.0.1:7890` 代理。**
`%APPDATA%\Docker\daemon.json` 里 `proxies` 指向本机 Clash。
Clash 一换端口或没开，`docker pull` 立刻失败，而报错是
`connecting to 127.0.0.1:7890 … actively refused` —— 看起来像网络问题，
实际是 Doker 的代理配置失效。**配 registry mirror 可以彻底绕开这个依赖**
（实测 `docker.m.daocloud.io` / `docker.1ms.run` 可用）。

## 4. 我自己的两次误判（记下来，免得算到系统头上）

| 现象 | 真相 |
|---|---|
| 门禁刷卡返回 **401** | 是我没带凭据。`/api/access/verify` 要设备密钥（`X-Gate-Key`）或管理员令牌；设备密钥默认为空 = 只允许管理员（fail-closed）。带令牌后是 **200** |

核对代码后撤掉了 —— 记在这里是因为"看到异常先怀疑自己"这个顺序不能省。

## 5. 已当场修掉的三条（都在 H2–H4）

| 修复 | 文件 | 守门方式 |
|---|---|---|
| 装 PostgreSQL 客户端 | `Dockerfile` | 构建期 `pg_dump --version`，装不上就炸 |
| **版本必须与服务端一致** | `Dockerfile`（`ARG PG_MAJOR=16` + PGDG） | 见下 |
| 备份/归档挂卷 | `docker-compose.yml` | `docker compose config` 可校验 |

CI 的 `docker` job 新增一步，把这三条一起守住：

```
备份 → 取出文件名 → 建临时库 → 用 main.py restore 恢复 → 逐表比对行数
```

**为什么不是只查"pg_dump 存在"**：H3 证明了存在并且能导出，dump 仍然可能恢复不回来。
这一步是"真的恢复一次"，它才是能抓住版本错配的那道门。

### 这道门当天就抓到了我自己的回归

H4 的修法（给 api 挂命名卷）**本身引入了新问题**，而且是 CI 把代码推上去之后
当场抓住的：

```
PermissionError: [Errno 13] Permission denied: 'var/backup'
```

原因：Docker 只在「卷是空的 **且** 镜像里该路径存在」时，才把目录的**内容与属主**
复制进新卷。而 `.dockerignore` 排除了 `var/` —— 镜像里没有 `/app/var`，
于是挂上来的卷根属主是 **root**，容器以 `appuser(10001)` 跑，mkdir 直接失败。
修法是在 Dockerfile 里先把 `/app/var/backup`、`/app/var/archive` 建好并 chown。

> 这一条特别值得记：**本机验不出来**——本机那次走的是 bind mount
> （Windows 上权限宽松），而 CI 走的是 compose 里的命名卷。
> 也就是说"我验过了"和"CI 验过了"在这里验的是**两条不同的路径**。
> 顺带一个方法论：改挂载方式之后要用**全新空卷**验一次，
> 别拿已经跑过的容器验（它的可写层里可能已经有那个目录了）。
>
> 这正是加这道门的意义 —— 它当天就还了债。

## 6. 结论

**系统本身没有崩，也没有数据错误** —— 走完六个环节，能走通的地方都走通了，
唯一的功能性缺陷（备份）已修并加了守门。

但试运行暴露的**共同模式**值得单独说：**这一轮补齐的功能，几乎都是"接口 + 测试"
到位、而"给人用的入口"没到位。**

* 审批 / 违约 / 通知 / 审计 / 门禁 —— 控制台上零入口（H1）；
* 备份 —— 有 CLI，但容器里跑不了（H2）、版本错（H3）、文件会丢（H4）；
* 通知 —— 有记录，但没人知道它在堆积、也没法一眼看全（H6）。

也就是说：**从"能不能用"的角度它是完成品，从"谁来用、怎么发现它坏了"的角度它还差一层。**
下一轮的重心建议从"继续加功能"转成"给已有功能配入口和可见性" —— 具体三件事：

1. 控制台补管理面板（审批待办 / 违约 / 通知 / 审计至少各一个只读列表）；
2. 三档健康检查里加"通知积压"与"最近一次备份时间"，让"坏掉"这件事自己浮出来；
3. 预约加改期（H5）—— 需要写代码，但它是用户能感知到的第一大缺口。

> 与 `docs/PROJECT-OVERVIEW.md` 第 9 节的关系：那份清单按"收益 ÷ 风险"排，
> 第一项是"放一个真实实验室试运行"。这份报告就是那次试运行的结果，
> 它把第一项从"跑起来看看"细化成了上面三件具体的事。
